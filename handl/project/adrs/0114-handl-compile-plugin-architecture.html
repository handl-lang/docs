ADR-0114: Handl Compile Plugin Architecture ​

Status ​

Proposed.

Context ​

Handl currently has three execution engines (tree-walk, bytecode, cranelift) that run Handl source at compile time and at runtime. It also has handl-emitters for emitting Language data fragments and plugin-sdkgen-emitter-file for writing generated SDK .hnl files. What it does not have is a generic plugin architecture for compiling Handl source to external target languages such as JavaScript, C, or WebAssembly.

Decision ​

Introduce a plugin-compile family of crates.

  • plugin-compile defines a Compiler trait and the target-agnostic CompilerInput (a parsed and type-checked Handl Ast plus optional metadata).
  • Per-target compiler crates implement Compiler:
    • plugin-compile-js — emits JavaScript for browser / Deno / Node.
    • plugin-compile-llvm — emits native code and object files.
  • The existing handl-emitters crate keeps its current role: emitting Language data fragments. It is not a source-to-source compiler.
  • host-cli gains a hnl compile <target> <file> subcommand that dispatches to the appropriate compiler plugin.
  • Compilers are selected by target name, not by file extension. The target triple / runtime is part of the compiler configuration.

JavaScript target ​

plugin-compile-js implements Compiler for JavaScript. It provides:

  • compile_to_string(input, config) -> Result<String, CompileError> — lower the type-checked Ast to a single generated JS string.
  • emit_module(input, out_dir) -> Result<JsOutputManifest, CompileError> — write one or more .js / .mjs files plus a runtime manifest.
  • runtime_prelude(runtime) -> String — choose the browser, deno, or node shim.

JsConfig.output_mode controls output form:

ModeUse case
esmECMAScript modules; default for Deno and modern browsers.
commonjsrequire / module.exports; for Node.
inlineSelf-contained <script> or eval string.

Value lowering: Handl primitives map to JS primitives; Arr/Obj become JS arrays/objects; Bytes becomes Uint8Array; Handle/Resource becomes an opaque reference; Pair and Either use tagged shapes; arrows become JS closures. Foreign calls lower to the js client package from ADR-0113: js.call("<module>.<name>", args) with js.errno() for errors. The runtime shim registers host functions by (module, name) so WebIDL/foreign binding metadata can be shared.

plugin-compile-js inlines js.call / js.error by default when the foreign object, method, and descriptors are known at compile time. For example, call("console", "log", [msg], ["js_string"], "js_void", false) compiles directly to console.log(msg). A configuration flag (--no-inline-foreign or keep_js_shim) opts out of inlining and keeps the runtime js client package for dynamic or generic foreign calls.

Consequences for the JS target: v1 does not emit source maps; stack traces point at generated JS. The inline and esm modes may include a # sourceURL=<input> comment for debugging.

Open questions:

  1. Source maps generated by the compiler or by a separate debug crate?
  2. Bundled handl-runtime.js per target, or granular helper imports?

LLVM target ​

plugin-compile-llvm implements Compiler for native object output using inkwell. It provides:

  • target() -> &str — returns "llvm".
  • compile(input) -> Result<CompilerOutput, CompileError> — build an LLVM module and emit a relocatable .o file.
  • set_target_triple(triple) — override the default host triple.

The lowering follows plugin-engine-exec-cranelift (crates/plugin-engine-exec-cranelift/src/compile.rs): each v2 Term compiles to fn(*mut EvalCtx, *mut Value) -> *mut Value; literal and name pools accumulate in constant arrays; every helper_v2_* runtime helper is declared extern "C". TargetMachine target initialization runs for the requested architecture before the module is built. FFI arrows call helper_v2_call_ffi_raw with the foreign name and descriptor from the name pool.

inkwell is preferred over raw llvm-sys to keep the builder API close to the existing cranelift/emitter patterns and to centralize LLVM lifetime bookkeeping.

Consequences for the LLVM target:

  • Adds a system-LLVM build dependency and an inkwell version coupling.
  • Emits object files that must be linked with the Handl runtime helper library, unlike the self-contained cranelift JIT path.

Open questions:

  • Share the exact helper_v2_* ABI with cranelift, or define a slimmer libhandlrt?
  • Where is cross-target validation enforced: CompilerInput, CLI, or TargetMachine creation?

Consequences ​

  • Compilers become first-class plugins alongside formatters, linters, and the test runner.
  • The Compiler trait can be implemented without touching the Handl core, as long as the input AST and type information are exposed.
  • The SDK generator (plugin-sdkgen-*) and the source-to-source compiler (plugin-compile-*) remain separate concerns: the former turns foreign APIs into Handl source; the latter turns Handl source into foreign code.
  • A new dependency appears: the compiler needs access to the type-checked AST and a type/grade projection API from plugin-engine-typecheck.
