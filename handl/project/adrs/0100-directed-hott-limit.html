ADR-0100: Directed Homotopy Type Theory as the Theoretical Limit ​

Status ​

Proposed.

Implementation status ​

The following 2-categorical and HoTT-oriented pieces are now wired into the codebase:

  • Term::Rewrite with source/target/witness and a value-carrying RewriteResult (Equal, NotEqual, Rewritten).
  • Law and rewrite rule registries on Language (laws, rewrites).
  • Term::Path, Term::Equiv, and Term::Transport variants and basic ValueModel/TypeModel semantics.
  • Transport uses Model::rewrite to move a value along a path/rewrite.

Higher directed HoTT features (higher cells, univalence-based transport, full fibrations, directed univalence, and (∞,1)-functor models) remain theoretical and are not implemented.

Context ​

ADR-0098 establishes that Handl is a category-graded arrow theory with one Term language and multiple Model interpreters. The Term data, Model trait, sort/grade/op declarations, and handler algebra provide the 1-categorical foundation.

However, the 1-categorical view is incomplete. The platform already has plugin-engine-transform for rewrites, plugin-engine-exec for evaluation, plugin-engine-typecheck for typing, and will need a compiler, optimizer, and theorem prover. These are not independent tools; they are different interpretations of the same structure. The rewrites themselves should be first-class.

The right long-term frame is a directed homotopy type theory (directed HoTT). In this view:

  • A sort is a type.
  • An arrow A ~> B is a directed path.
  • A rewrite f => g is a 2-path.
  • A Model is a directed (∞,1)-functor.

This ADR records the decision to adopt directed HoTT as the theoretical limit and to design the Term data and Model trait so that 2-cells and paths can be added without replacing the 1-categorical architecture.

Decision ​

1. The Term 2-category ​

The Term data in ADR-0098 is a 1-category:

text
0-cells: sorts
1-cells: Term arrows (Arr, Op, Seq, First, Choice, Loop, App, Iter, Child)

We enrich it to a 2-category by adding a Rewrite term constructor:

rust
pub enum Term {
    Arr { value: Value },
    Op { name: String, args: Vec<Term>, ... },
    Seq { ... },
    First { ... },
    Choice { ... },
    Loop { ... },
    App { ... },
    Iter { ... },
    Child { ... },

    /// A 2-cell: a rewrite, optimization, law, or proof step.
    Rewrite {
        source: Box<Term>,
        target: Box<Term>,
        witness: RewriteWitness,
    },
}

pub enum RewriteWitness {
    /// A declared law or rewrite rule from `Language` data.
    Rule { name: String },
    /// A beta/eta step generated by the type model.
    Compute,
    /// An inline hint from a handler.
    HandlerHint,
    /// A user-provided or compiler-inserted cast.
    Cast,
}

A Rewrite is a directed 2-cell. It explicitly names a source arrow, a target arrow, and a witness for why one rewrites to the other. The Term language is now a presented 2-category.

2. The Language as a presented 2-category ​

Language data gains two new declaration forms: law and rewrite.

handl
law first_compose :
  First(g >>> h) => First(g) >>> First(h)

law add_zero :
  add(0, x) => x

rewrite for_to_iter :
  for (i from 0 to n) body
  =>
  iter(n, (i) ~> i < n, (i) ~> (i + 1, body(i)), 0)

A law is a 2-cell that is expected to hold semantically. A rewrite is a 2-cell that the compiler or optimizer may use to replace the source with the target. Both are data, not Rust code.

The Language is now a presentation of a 2-category:

  • sort declarations = generating 0-cells
  • grade declarations = generating 0-cells that are propositions
  • op declarations = generating 1-cells
  • law/rewrite declarations = generating 2-cells
  • handler declarations = equations for 1-cells

3. A Model is a 2-functor ​

The Model trait from ADR-0098 becomes a 2-functor:

rust
pub trait Model {
    type Value;

    /// Interpret a 0-cell (sort) as a carrier.
    fn carrier(&self, sort: &TaggedValue) -> Result<Carrier, LangError>;

    /// Interpret a 1-cell (term) as a value/function.
    fn run(&self, term: &Term, incoming: Self::Value, ctx: &ModelCtx)
        -> Result<Self::Value, LangError>;

    /// Interpret a 2-cell (rewrite) as an equality or transformation,
    /// using the provided `incoming` value.
    fn rewrite(
        &self,
        source: &Term,
        target: &Term,
        witness: &RewriteWitness,
        incoming: &Self::Value,
        ctx: &ModelCtx,
    ) -> Result<RewriteResult, LangError>;
}

RewriteResult is the model-specific meaning of a 2-cell:

rust
pub enum RewriteResult {
    /// The two sides are equal (value model, type model).
    Equal,
    /// The source should be replaced by the target (optimizer model).
    Replace,
    /// The target is already proved (theorem prover model).
    Proved,
    /// The source compiles to the target (compiler model).
    Compiled,
    /// The model does not interpret this kind of rewrite.
    Unsupported,
}

The ValueModel uses rewrite to check that both sides of a law produce the same value. The TypeModel uses it to check that both sides have the same type. The CompilerModel uses it to replace the source with the compiled target. The OptimizerModel uses it to rewrite Term in place.

All models are functors from the same Language 2-category. The difference is only the target 2-category.

5. Syntax for rewrites and paths ​

A Term is an arrow. A Rewrite is an arrow between arrows. The syntax uses => for 2-cells:

handl
law first_compose :
  First(g >>> h) => First(g) >>> First(h)

rewrite add_zero :
  add(0, x) => x

A path (undirected equality) uses =. A directed path (arrow) uses ~>.

handl
path p : a =_Number b      -- a path/identity proof
arrow f : Number ~> Integer  -- a directed arrow
rewrite r : f => g         -- a 2-cell between arrows

6. Univalence and transport ​

The key HoTT axiom is univalence:

text
(A ≃ B) → (A = B)

An equivalence of sorts gives an equality of sorts. This means Handl can declare two sorts equivalent and then transport operations between them.

handl
sort Number = () ~> [Addable, Comparable, Serializable]
sort Integer = () ~> [Addable, Comparable, Serializable]

equiv Number Integer = (to_int, to_num, roundtrip)

add_Number : (Number, Number) ~> Number
add_Integer : Integer ~> Integer = transport add_Number along (Number = Integer)

The transport operator says: because Number and Integer are equivalent, the arrow add_Number can be moved along the path to become an arrow between Integer and Integer.

The CompilerModel uses univalence to compile Number and Integer to the same target representation when they are equivalent. The TypeModel uses it to allow a Number value to be used where an Integer is expected, and vice versa, with the equivalence as evidence.

7. Grades as propositions ​

In HoTT, a proposition is a type with at most one element (h-level 1). A grade is a proposition over a sort.

handl
grade Addable = { T : Sort | has_add(T) }

Addable is the collection of all sorts T equipped with an add operation, where any two such operations are equal. The grades clause on a sort is a list of proof objects:

handl
sort Number grades Addable, Comparable, Serializable

Number is a value of type Sort, and the grades clause provides proofs that Number : Addable, Number : Comparable, and Number : Serializable. These proofs are values in the TypeModel.

The op declaration is a function in a fibration:

handl
op add<A: Addable> : (A, A) ~> A

The grade constraint A: Addable is a proof that the input sort A has the Addable grade. The TypeModel checks this proof; the ValueModel dispatches by it.

8. Directed paths ​

Ordinary HoTT has undirected paths (a = b). Directed HoTT adds directed paths (A ~> B). In Handl:

  • A ~> B is a directed path from A to B.
  • f => g is a 2-path from arrow f to arrow g.
  • a =_A b is an undirected path from value a to value b.

The directed part captures computation (arrows go from input to output). The undirected part captures equality (values are equal regardless of direction).

A Model is a directed (∞,1)-functor: it maps directed paths to functions and undirected paths to equalities. The ValueModel maps ~> to functions and = to equality of values. The CompilerModel maps ~> to target functions and => to compiler transformations.

9. The Term directed (∞,1)-category ​

The full structure is a directed (∞,1)-category:

text
0-cells:   sorts
1-cells:   arrows  A ~> B
2-cells:   rewrites  f => g
3-cells:   rewrites between rewrites
...       ...

For implementation, we truncate at 2-cells. The Term data has Rewrite as the 2-cell constructor. Higher cells are not represented directly, but the TheoremProverModel can reason about them.

10. Relation to existing ADRs ​

  • ADR-0098: the 1-categorical fragment. This ADR generalizes it.
  • ADR-0052: the arrow calculus is the 1-cell language.
  • ADR-0094: the transform engine is the OptimizerModel over the Term 2-category.
  • ADR-0070: refinement types are grades with predicates.
  • ADR-0081: AST child roles are part of the Language presentation.

This ADR does not replace ADR-0098. It sits on top of it. The 1-categorical implementation remains valid; the 2-categorical and HoTT features are added as Term and Language data.

11. Implementation implications ​

  1. Add Term::Rewrite. Extend the Term enum with Rewrite.
  2. Add law and rewrite declarations. Extend the canonical language data with these forms.
  3. Extend Model trait. Add rewrite method.
  4. Make plugin-engine-transform the OptimizerModel. It is already a Model over Term.
  5. Add transport and equiv surface forms. These are 1-cell operators derived from univalence.
  6. Add Path sort. Path(A, a, b) is the sort of paths from a to b in A.
  7. Keep the 1-categorical engine. Do not require 2-cells for evaluation. The ValueModel can return Unsupported for Rewrite nodes.

Consequences ​

Positive ​

  • Replaces plugin-engine-transform with a first-class OptimizerModel.
  • Makes compiler correctness a consequence of functoriality, not a separate proof.
  • Makes sort/grade/op/law/rewrite all data, not engine code.
  • Gives a unified theory for evaluation, typechecking, compilation, optimization, and proof.
  • Provides a roadmap for full dependent types via Path, transport, and univalence.
  • Explains why Runtime was renamed to Model: a Model is a functor, and a Runtime is one implementation.

Negative ​

  • Adds Term::Rewrite and Model::rewrite, which is a significant data change.
  • Requires law and rewrite grammar and desugaring in canonical data.
  • Path and transport require dependent sorts and grade reflection.
  • HoTT is not trivial; the TypeModel becomes more complex.
  • The CompilerModel must prove it respects 2-cells, or at least trust them.
  • Directed HoTT is still research; no off-the-shelf implementation exists.
