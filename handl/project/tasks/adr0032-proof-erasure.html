ADR-0032 Item 6: Proof Erasure at Runtime ​

Goal ​

Wire proof-term erasure into the Runtime::run_checked pipeline so that the typechecker can tell the runtime which AST nodes are proofs, and the runtime replaces those nodes with a cheap erased/null node before evaluation. This removes the runtime cost of carrying proof terms while keeping the static type-safety guarantees intact.

Notes / open questions ​

  • What counts as a proof term today?

    • Concrete singleton proof values are type.refl (equality proof) and type.is_evidence (membership proof), both minted by TypeRegistry::construct as tagged JSON objects with __tag__ and __registry__ keys.
    • type.empty is the uninhabited proposition; if a node ever synthesizes it, it is also safe to erase.
    • type.eq and type.membership are proposition types / type families, not proof values. Their inhabitants are type.refl and type.is_evidence respectively, so only those inhabitants should be erased.
    • data constructors are currently ordinary tagged records; there is no proof or erased marker, so user-defined proof types are not yet recognized by the erasure pass.
    • Verdict::Proven / Verdict::Blocked are compile-time outcomes of the predicate checker, not runtime values. They only control whether the runtime_assert pass runs.

  • Where should erasure run?

    • The chosen design is an AST pass between typecheck and eval.
    • The typechecker records per-node types and returns them in TypecheckResult::node_types.
    • Runtime::run_checked calls erase_pass::apply_erase after the runtime_assert lowering and before eval.
    • Erasure is not done inside the typechecker (too engine-specific) and not as a runtime eval scheme (that would still build the proof value before discarding it, defeating the purpose).

  • Precondition / blocker:TypecheckResult currently only returns the root type. Subtask 2 (per-node type map) is the main blocker for the full erase pass.

  • Open question — ordering relative to runtime_assert_pass: Proposed order is typecheck → runtime_assert_pass → erase_pass → eval. This keeps blocked runtime checks intact and only nullifies nodes whose type is already a singleton proof. Revisit if any erased constructor is needed by a runtime_assert predicate.

  • Open question — data proof constructors: Built-in equality/membership proofs are covered by the type.refl / type.is_evidence tags. User-defined data proof types (e.g. data Eq(a, b) = Refl) will need an additional desugaring signal, such as an erased field on DataConstructor, before the erase pass can handle them. This is tracked as the optional follow-up in Subtask 4.
