mlopt-kit — the modular handl composition, proven end to end ​

Date: 2026-10-19 · Surface: packages/mlopt-kit/ (new Rust crate, root cargo workspace) · Gate: cargo test -p mlopt-kit — 16/16 green.

What landed ​

mlopt-kit is mlopt's seam to the modular handl stack — a plain Rust library crate (the mlopt-native layout precedent: no PyO3, no Python changes beyond a uv-workspace exclude line). It assembles the smallest honest runtime for mlopt's use:

  • Language — handl_kit_data_canonical::language_from_yaml() (the canonical Language as data), installed process-wide via plugin-lib-handl::install_default_language so lazily-built .hnl module bridge runtimes bind it (ADR-0128 §"the 0.8 seam").
  • Engines — the three the canonical kit defaults to: data lex (DataLexerEngine), pratt parse (PrattEngine), tree-walk eval (TreeWalkEngine). No sdkgen/compile/lint/lsp. Engine selection is by name through EngineRegistry/RuntimeConfig; CatoptKit::new_with_registry is the injection seam for more later.
  • Modules — host-tensor's TENSOR_HNL interface as a HandlModule over tensor_op_registry() (all 18 tensor.* ops), in a ModuleRegistry layered under handl_runtime::fp's field_access/fanout host fns. field_access makes tensor.matmul(a,b) dispatch with no injected globals: unbound tensor → "tensor" → "tensor.matmul" → ModuleLookup → OpFunction.
  • Imports — a ModuleLoader is wired into the eval engine (and into the loader's own engine for nested imports), so import "./f.hnl" works relative to module_root, and CatoptKit::new_with_project reads .handl.toml [dependencies] via handl_platform::resolve_dependencies.
  • run_tagged — a second wired engine kept for the TaggedValue-returning eval path (eval_tagged), so a tensor op result can be observed as the real TaggedValue::Tensor variant with no serde_json::Value round-trip.

Deps float on main as git deps (kernel/lang/platform/host-tensor); the local-override story is ~/.cache/devin/handl_deps.env (git insteadOf → ~/GitHub/handl-lang/* checkouts) with the handl-lang [patch] convention documented in the root Cargo.toml.

Verified end to end (tests/compose.rs) ​

  • tensor.to_list(tensor.matmul(from_list([[1,2],[3,4]]), from_list([[5,6],[7,8]]))) → [[19,22],[43,50]] through the assembled runtime — real .hnl → real tensor work.
  • run returns the {"__tensor__":…} wire form; TaggedValue::from decodes it to TaggedValue::Tensor (shape [2,2], data [19,22,43,50]); run_tagged returns the Tensor variant directly — never an Obj fallback.
  • Chained ops inside one program (add(matmul(a,b), ones)) — the tensor round-trips through the Function boundary each hop.
  • conv2d (1×1 NCHW) and batch_norm (eval mode, eps=0) smokes — both match host-tensor's own spec values.
  • tensor.derive("batch_norm") → "tensor.batch_norm_backward"; unpaired → null — the optimization-loop surface.
  • .handl.toml name resolution works: a temp project with host-tensor = { path = "host-tensor" } (the embedded TENSOR_HNL vendored as index.hnl) supports both from "host-tensor" import tensor and import * as t.
  • A consumer-authored .hnl module (linalg.hnl with a from "host-tensor" import tensor header and an export double_matmul arrow) imports and runs — the shape a mlopt-side .hnl module would take.

Named gap — closed (2026-10-19, second pass) ​

A checked-in .handl.toml can now name the host-tensor dep portably: platform 90853ec2 added the git-package→dir bridge — [dependencies] entries accept { git = …, rev|branch|tag } and a [patch] table is the consumer-side local override (the Cargo [patch]/dev-link story: a patch whose directory exists wins, a missing one is inert). packages/mlopt-kit/.handl.toml declares host-tensor = { git = "https://github.com/handl-lang/host-tensor", branch = "main" } + [patch] → the sibling checkout's src/ (the dir holding index.hnl); an unpatched git dep resolves to its ~/.handl/pkg/<name> cache slot — the dir the ADR-0010 fetch hook will populate (a symlink there is today's stand-in). Both resolution arms are asserted in tests/conv_bn.rs.

The shipped consumer — hnl/conv_bn.hnl, the conv+BN fold end to end ​

The crate now ships the .hnl program mlopt's e-graph optimizes: conv_bn is the unfolded batch_norm(conv2d(x, W, b), γ, β, μ, σ²) composite — the BATCH_NORM_RULES/CONV_FOLD_RULES fold site — and conv_bn_fold is the minted rewrite's RHS evaluated: s = γ·rsqrt(σ²+ε) per channel (the op surface has no elementwise pow, so channel_scales is a while-loop over the materialized stat lists using scalar **), W′ = W∘reshape(s, (C,1,1,1)), b′ = b∘s + (β − s∘μ), then a single conv2d. bn_adjoint/bn_grad compose tensor.derive/batch_norm_backward — the registered-adjoint surface. tests/conv_bn.rs proves TaggedValue::Tensor results and exact folded-vs-unfolded agreement on a dyadic fixture (conv out [[12,15],[6,5]] → BN/folded [[37,46],[4,3]]; dx/dγ/dβ [3,3,1,1]/[27,2.5]/[2,2]). The consumer story the fold's premise-pay measurement (fold-cost-single-source.md) pointed at: the same program the e-graph folds is the program the kit runs.

One environment note ​

The tree-walk engine recurses deeply enough on ordinary expressions to overflow libtest's 2 MiB default test-thread stack (conv2d's 4-deep literals hit it). Both upstream suites carry the same knob — repo-root .cargo/config.toml sets RUST_MIN_STACK = 32 MiB, matching kit-canonical/.cargo/config.toml. Not a composition blocker — an upstream-documented constraint.

What this is not (yet) ​

No Python surface (that is mlopt-native's maturin shape when needed); no bytecode/typecheck/compile engines registered (the registry seam admits them by name); no package fetch — an unpatched git dep resolves to its ~/.handl/pkg slot, which nothing populates yet (the ADR-0010 fetch hook is upstream's follow-up; a checkout/symlink there is the stand-in). The e-graph itself still lives Python-side — the kit runs the folded program; lowering mlopt IR to .hnl is the direction the seam opens, not something this crate does.
