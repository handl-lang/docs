Overview — where the kernel work is, and the M1 plan ​

Date: 2026-10-27 · for review

0 · Refactor context (ADR-0159, ADR-0160) ​

The domains keep their lab form for now, but the naming and the endpoint are settled:

  • ADR-0159 — the optimizers become hnl optimize --domain graph|kernel commands (ext-*) once three triggers hold: a caller that is not the researcher, a surface unchanged for four weeks, and a shared referee. Wrap the Python core behind a port; do not rewrite it in Rust.
  • Naming — the family is opt-*: opt-graph (today graphopt), opt-kernel (today kernelopt). A third member (opt-schedule) only on the rule of three.
  • ADR-0160 (allocated) — the kernel IR is Term + kit-declared ops; the six combinators stay closed.
  • Generic core stays a library — egraph, discovery, eqsat are domain-free; a domain is rules + cost model + adapters.

Everything below is lab-form: repos, drivers, own harnesses. No ext wrapper, no FFI seam, until the triggers fire.

1 · The thesis ​

Hand-tuning kernels is expensive, so it is only bought for popular shapes on popular hardware. A machine that proposes, prices and certifies kernels can cover the long tail. The moat is not one fast kernel — it is the referee (honest measurement), the collapsing cost per experiment, and certification.

3 · What this session proved ​

  • Kernel margin (valid): our int4 GEMV beats awq_gemm cold on three of four layer shapes — 2.96× / 1.52× / 1.35×, exact.
  • It reaches the model (valid): substituted into vLLM with the checkpoint tensors snapshotted before repacking, output is token-identical and the model is 29.2 % faster (1164.6 → 824.1 ms, 25/25 paired rounds, decode, one 4 GB laptop GPU).
  • Three retractions: a fake 3.3× (fp16 atomics), a fake −3.1 % (too few rounds), a fake −28.5 % (wrong AWQ nibble order). All caught by the harness, all published as retractions.
  • The bug worth remembering: AWQ packs 8 int4 per int32 in the order [0,4,1,5,2,6,3,7]. My reference used the same wrong order, so it validated itself. A self-written reference proves self-consistency, not correctness.

What is still not true: the machine did not find that kernel — I wrote it. It swept 48 configs of my design. Closing that gap is M1.

Visibility (ADR-0150): lib-kernel-ir public; compile-triton, the runtime binding and any ext-opt-* are tooling — private until done.

M1 gate: four variants generated from Terms, all exact, and at least one within the hand kernel's 58.9 µs cold on down_proj. Kill: if a fixed lowering cannot match hand-written Triton on one operator, generalising is wasted work — keep hand-writing kernels and use the search only for configs.

Three corrections that shaped it: a kit is a manifest of libs (so lib-kernel-ir + kit-kernel-ir, not one thing); compile-triton is Rust like the rest of the family; and there is no new schema — the IR is Term, so certificate, sink, sieve and cost model all apply unchanged.

Two-stage schedule, stated for attribution: our IR picks blocks and split; Triton picks pipelining, vectorization and layouts.

7 · Decisions (resolved 2026-10-27) ​

1. M1 covers two operators: qgemv and gate_proj — the second has the opposite geometry (large N, small K), so the space has to generalise rather than overfit one shape. Gate for qgemv: within the hand kernel's 58.9 µs cold. Gate for gate_proj: no worse than today's awq_gemm (57.8 µs), i.e. at least 0.95× — it is the operator we currently lose, and turning a loss into a tie is the honest first target.

2. Public, and the names change: there is no "cuda" in this design. Triton targets NVIDIA and AMD, and the IR carries resource grades rather than assuming one vendor. So:

oldnewwhy
lib-kernel-irlib-kernel-irit is a kernel IR, hardware-agnostic
kit-kernel-irkit-kernel-irkit = manifest of libs
lib-triton-qgemv (M2)lib-triton-qgemvthe runtime binding executes Triton, not CUDA
compile-tritonunchangednames the target language, which is accurate

The device class (sm_count, bandwidth, L2) enters as grade data, not as a name, so a second vendor is a calibration, not a rename.

3. The ADR lives in kernelopt — the domain that owns the IR and the search records the decision it depends on.

4. Ambition: both breadth and depth. That has one consequence for sequencing: depth first (two operators proven end to end), then breadth (formats × shapes), because breadth multiplies the candidate count and therefore requires the compile cache before it, not after.

Amended M1 boundary ​

In: ADR (kernelopt) · lib-kernel-ir with nine ops + denotations · compile-triton for qgemv and gate_proj (4 split_k variants each) · equality gate vs awq_gemm · search driver.

No kit in M1. A kit exists to assemble several libs; with one lib there is nothing to assemble. kit-kernel-ir arrives at M2, when the lib-triton-qgemv binding, the cost tables and the base types have to meet. (Same reason kit-prelude-lang exists and a single lib does not.)

M1.5 (before breadth): compile cache + candidate pruning by roofline bound. Without it, breadth is rate-limited by triton.jit, not by ideas.

Still out: lib-triton-qgemv binding, FP8/GPTQ, compile-cuda.
