Kits ​

A kit is a curated environment: a kit.hnl v1 manifest ({ name, description, license, libs }) that assembles lib-* packages into a ready-to-use surface for a domain — CLI apps, HTTP servers, browser interop, testing, or the mlopt research stack. Kits are pure curation: no plugins, no entry glue; each listed package's own pkg.hnl deps pull its contracts and transitive backends.

Application kits ​

KitWhat it assembles
kit-cli-appBuild CLI applications — argv parsing (mri), stdio, POSIX fs/env/time, child processes, JSON, collections
kit-web-serverServe HTTP from handl — epoll accept loop, HTTP/1.1 codec + routing, TLS, WebSocket, JSON
kit-testIn-language test surface — test/property/benchmark/fuzz/snapshot/assert plus deterministic rand and posix stubs
kit-pkgThe package kit — .handl.toml project discovery and dependency wiring

Interop kits ​

KitWhat it assembles
kit-web-browser-iteropBrowser/client-side JS interop — call/invoke/await into JS, fetch and WebSocket over generated WebIDL bindings, JSON + JS str backend
kit-web-worker-iteropWeb Worker interop for handl-on-JS — JS call/invoke/await surface plus data plumbing (JSON, serialize port, str-js backend)

MLOpt kits ​

The mlopt research game (see Products) has its own kit family — domain kits that wire tensor, carrier, and discovery machinery:

KitWhat it assembles
kit-torchPyTorch integration for the mlopt game
kit-cudaCUDA-graph delivery mechanism for the mlopt game
kit-carriersSemantic carriers — online-softmax monoids
kit-discoveryLaw-discovery engine — census, proposal, verification
kit-host-tensorHost-tensor backend — mlopt_core.ports.Sink over native tensor ops

Kits are data, so composing one is editing a manifest: pick the libs, let pkg.hnl deps resolve the rest. The kits that bootstrap the toolchain itself ship with the platform layer.
