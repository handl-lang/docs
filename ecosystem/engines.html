Engines ​

Engines are the pluggable implementations of Handl's language operations. A language definition is data — syntax, grammar, AST shapes, eval schemes, and type rules live in Language records, not in engine code. An engine interprets that data, so swapping one changes how a language runs, not what it means.

Every operation follows the same shape: a small abstraction crate owns the contract (marker type, request, trait, shared helpers) and one or more engine crates implement it. The kit decides which engine fills each slot.

The operations ​

OperationContractEngines
lextool-lextool-lex-pattern — data-driven rules
parsetool-parsetool-parse-pratt — Pratt, grammar rows
transformtool-transformtool-transform-rewrite — rule-interpreting
typechecktool-typechecktool-typecheck-nbe — normalization by evaluation
evalexecexec-tree-walk (reference), exec-bytecode (stack VM), exec-cranelift (JIT/object)

Two further families sit alongside: tool-compile-* lowers Terms to concrete targets (see Compiler backends), and the ext-* crates package the same operations as dynamic hnl extensions (see Extensions).

Shared substrate ​

  • engine — Term, Model, and the arena view every engine uses.
  • engine-eqsat — the e-graph search interpretation over kernel Terms: saturation and extraction via handl-egraph, with laws, guards, and cost specs as kit data.

Tooling instruments ​

The tool-* family beyond the five core operations:

  • tool-fmt — data-driven AST formatter; renders an Ast using only language data, no hardcoded kinds.
  • tool-lint — rule-based linter over a lang.lints table plus named native checks.
  • tool-test — bootstrap test runner: discovery, tag/filter predicates, scheduling.
  • tool-watch — cross-platform filesystem watcher: typed events, filters, debounce.
  • tool-codemod — the spec/model layer of the declarative codemod engine.

Compiler backends ​

tool-compile-* emitters lower Handl Term arrow graphs to concrete targets. Canonical/debug targets round-trip the IR itself; the performance targets emit real code.

RepoTarget
tool-compile-termTerm JSON — canonical form
tool-compile-handlHandl source (Hughes arrow dialect)
tool-compile-sexpS-expressions
tool-compile-dotGraphviz DOT graphs
tool-compile-jsJavaScript
tool-compile-llvmLLVM IR — the escape hatch to native code
tool-compile-tritonTriton kernels (GPU)
tool-compile-cudaCUDA C++ — templated __global__ + extern "C" launcher

Emitters decline uncovered ops by name rather than emitting stubs — a compile failure is explicit, never silent.

References ​

The design lineage is academic: equality saturation comes from the e-graph literature (egg/egglog), normalization-by-evaluation from the type-checking literature, and Pratt/precedence parsing from classical parser theory. See the bibliography for the foundations; implementation-specific references are collected under "Tooling and implementation" there.
