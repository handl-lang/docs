Handl ecosystem ​

Handl is a modular language infrastructure built around a categorical, runtime-independent IR. Its foundation is a closed arrow calculus with globular higher-categorical structure, allowing computation, laws, and transformations to share a common representation.

The ecosystem separates this foundation from the engines that process it, the abstractions built on top of it, and the environments in which it operates.

1. Kernel ​

The Kernel defines Handl's computational foundation: its arrow calculus, IR, value representation, and language schema. It is a closed arrow calculus (LWY + Sanada) extended with graded effects and globular higher-categorical structure, where programs, laws, and transformations are all data.

The Kernel provides a stable foundation without prescribing a particular runtime or execution strategy. See the paradigm for what the calculus buys you.

2. Engines ​

Independent components that process Handl representations. Engines can analyze, transform, compile, or execute the IR.

Compilation

LLVM (native), Triton, CUDA emitters.

Execution

Cranelift JIT, bytecode VM, and the tree-walk reference interpreter.

exec-craneliftexec-bytecodeexec-tree-walk
Transformation

IR-to-IR rewriting, desugaring, and optimization.

tool-transform-rewrite
Language processing

Lexer, parser, typechecker, linter, and formatter engines.

tool-lex-patterntool-parse-pratttool-typechecktool-linttool-fmt

Engines are interchangeable consumers and processors of the shared representation, not intrinsic parts of the Kernel. In the repo taxonomy they are the tool-* instruments (lex/parse/transform/typecheck/fmt/lint), the exec-* eval backends, and the engine/engine-eqsat search engines — the tool-compile-* emitters sit alongside as compiler backends. Each operation is also packaged as a dynamic ext-* extension — see Engines and Extensions for the per-repo maps.

3. Libraries (lib-*) ​

Reusable Handl libraries (.hnl) providing foundational and domain-specific functionality, such as mathematics, strings, logic, and other utilities. See Libraries for the port/impl convention and the full categorized map.

Libraries provide runtime-agnostic abstractions: the same APIs can be used across different execution environments, with runtime-specific implementations preserving compatible interfaces and semantics. This allows application code and higher-level libraries to remain independent of the underlying runtime.

4. Kits (kit-*) ​

Curated collections of libraries and components targeting particular environments or use cases, such as testing, server-side development, and web services. Kits provide ready-to-use environments by assembling compatible libraries, engines, and supporting components. See Kits for the manifest format and the public kits.
