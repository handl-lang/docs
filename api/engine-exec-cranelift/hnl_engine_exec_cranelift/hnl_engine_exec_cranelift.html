hnl_engine_exec_cranelift::ACTIVE_EVAL_CTX ​

Constant: $crate::thread::LocalKey<std::cell::Cell<*mut EvalCtx>>

The cranelift [EvalCtx] currently executing a clause application through the tree-walk interpreter (apply_value_treewalk).

Arrow values run in the tree-walk, so a resume called from inside a clause body is applied there; the shared driver it reaches (native_ops::drive_shared_resumption) recovers &mut EvalCtx here. Save/restore keeps nested applications consistent, and a null pointer means no cranelift evaluation is active.

Struct

The evaluation context shared between the Rust helpers and the native compiled code.

This struct is owned by the engine on the Rust side. A raw pointer to it is passed to the cranelift-compiled functions, which pass it back to the extern "C" helper functions. All access is single-threaded.

Safety ​

The lang, ast, and modules raw pointers are valid for the lifetime of the eval call (the engine borrows them from the EvalEngine::eval parameters). The compiled map holds function pointers into JIT-allocated memory that remains valid as long as the JITModule is alive — the compile module keeps the module alive via the CompiledResult.

hnl_engine_exec_cranelift::apply_value_treewalk ​

Function

Apply a value to args via the reference tree-walk engine.

ADR-0106: arrows are self-contained data — body_def is a standalone substituted AST arena, binds the residual bindings, handlers the carried deep handlers — so there is no per-arrow compiled function to look up: the body arena did not exist when ctx.compiled was built. The tree-walk engine interprets the arena directly; ctx supplies the ambient services (language schemes via ctx.lang, module dispatch via ctx.modules, the import resolver, and host globals).

unpack_arr is the ADR-0060 single-array-arg unpack used by the call/App surface forms (apply_closure_value); flow and __term__ bound-arrow dispatch pass false so a list input stays one argument.

Safety ​

ctx must be a valid &mut EvalCtx. ctx.lang must point to a valid Language — the standalone driver (lang null) cannot interpret body_def arenas and reports an error instead.

fn apply_value_treewalk(ctx: & mut EvalCtx, callee: handl_value::TaggedValue, arg_vals: Vec<handl_value::TaggedValue>, unpack_arr: bool) -> *mut handl_value::TaggedValue

hnl_engine_exec_cranelift::arr_dispatch ​

Function

Dispatch a payload-resolved arr <op> against a concrete operand. Module: compile ​

Term -> cranelift IR compilation (ADR-0052) ​

This module compiles [Term] data — the arrow-calculus kernel — to native code via cranelift, targeting the six combinators (Arr, Seq, First, Choice, Loop, App).

Compilation strategy ​

Each node's Term is baked into the IR at compile time — no runtime scheme lookup occurs. The compiled function has signature fn(*mut EvalCtx, *mut Value) -> *mut Value, where the second parameter is the incoming value flowing through the arrow (top-level calls pass a boxed Null).

  • Control flow is native: Choice compiles to native brif/jump with a merge block; Loop compiles to native back-edge blocks with a max-iteration counter in a stack slot.
  • Value operations call Rust helpers: pair/Either construction and extraction, native op dispatch, variable load/store, child evaluation, and closure application are native calls into extern "C" helper_v2_* functions defined in [crate].
  • First is inline: unlike the bytecode VM's FirstOp sub-program, cranelift has native control flow, so First unpairs the incoming pair, compiles inner inline with fst as the incoming value, then re-pairs the result with snd.

Loop native-code model ​

Loop { body } compiles to a native loop with three exit conditions. The incoming value is saved in a local; the initial pair (incoming, Null) is constructed and fed to body. After each body iteration, the result is inspected by helper_v2_loop_check, which returns a tag: 0 = Either left (terminate with the carried value), 1 = Either right (loop back with the new state), 2 = pair (single-step — terminate with fst). For the loop-back case, a new pair (saved_incoming, new_state) is constructed and control jumps back to the body block. A max-iteration counter (100_000) in a stack slot prevents infinite loops, matching the tree-walk and bytecode VM guards.

Derived step ops ​

All four derived step ops from ADR-0052 are supported:

  • loop_step (the ergonomic loop surface lowering): its carried sub-scheme arg (the body closure) is compiled inline like any other Arr.arg; the Loop combinator passes the current pair (in, state) as incoming to apply_native, which dispatches to prim_v2_loop_step. That helper applies the body closure via apply_closure_value (a recursive call into the closure body's compiled native function).

  • while_step/for_step/fix_step (built by plugin-lib-stdlib::arrow_iter::{while_loop,for_loop,fix_loop}): these carry cond/body sub-schemes that must be re-evaluated per iteration with the current value (extracted from the loop pair) as incoming. The compiler calls helper_v2_derived_step_arg_incoming to extract the appropriate incoming value from the pair at runtime, then compiles the args inline with that value as incoming. The compiled args run each iteration (they're inline in the loop body block), using the runtime arg-incoming value. apply_native still receives the full pair as incoming (the op handlers extract current/state from it).

Module: standalone ​

Standalone bootstrap entry points (ADR-0044 Phase 8) ​

These #[unsafe(no_mangle)] pub extern "C" functions provide the C ABI bridge between a generated C main driver and the Rust evaluation context. The standalone binary is produced by linking three pieces:

  1. The cranelift-emitted .o file — contains the node_N native functions (compiled from the AST via compile_all_nodes_object). These are declared Linkage::Export so their symbols are visible to the linker.
  2. This crate as a static library (crate-type = ["staticlib"]) — exports the helper_* symbols (the runtime stub) and the handl_standalone_* entry points defined here.
  3. A generated C main driver — declares extern prototypes for the node_N functions and the handl_standalone_* entry points, builds the function-pointer table, calls [handl_standalone_init] → [handl_standalone_run] → prints the result → [handl_standalone_destroy].

The driver embeds the serialized Ast, literal pool, and name pool as JSON string constants (produced by [crate::CraneliftEngine::compile_to_executable]).
