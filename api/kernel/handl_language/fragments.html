Module: lexer_rule ​

Lexer rule fragment definitions. Lexer rule fragment definitions.

A [LexerRuleDef] carries the pattern data a data-driven lexer engine uses to recognize one token kind in source text (ADR-0044 §1). Like token kinds and AST shapes, lexer rules are structural facts ("this is how you recognize a token.number"), so they merge with union (idempotent) semantics — re-declaring the same rule id is a no-op (first wins).

The identity key is the rule id (not token_kind), so multiple rules can produce the same token kind (e.g. lex.bool.true and lex.bool.false both produce token.bool).

Module: lint_rule ​

Lint rule fragment definitions (ADR-0097 — Lint Rules as Language Data). Lint rule fragment definitions (ADR-0097 — Lint Rules as Language Data).

A lint rule maps a check over source or AST to a diagnostic. Rules live in the Language lints fragment set — adding a rule to a language is a data change, never an engine recompile.

This crate holds only the data: [LintCheck] and [LintFix] are the rule vocabulary — they are interpreted by lint engines (e.g. hnl-engine-lint), never executed here. The Native check variant is the disciplined escape hatch (same pattern as TransformRule::Native): dispatch stays in LintRuleDef data while the implementation — scope analysis, whole-source checks, host-tool composition — is supplied by a native-lint registry.

Serde representation ​

All enums use serde's default externally tagged representation, matching TransformRule and friends: a check is {"Match": {"node_kind": …, "when": …}} or {"Native": "scope.unbound-wire"}.

Module: lsp ​

LSP surface fragment definitions (ADR-0100). LSP surface fragment (ADR-0100).

A LspDef is a generic, method-keyed declaration of which LSP requests a language supports and which data-driven rules the plugin-lsp engine should run for each. The engine is method-agnostic: it looks at the LSP method string, evaluates the rule list in order, and dispatches each rule by its kind field. All rule configuration lives in the config map, so a language can invent rules for any future kind the engine learns without changing the Language schema.

Module: option ​

Option schema fragment definitions. Option schema fragment definitions.

OptionSchema is defined locally here rather than re-exported from handl-platform. The platform's OptionSchema is not serde-serializable (its OptionScope enum lacks serde derives and it is coupled to the Plugin/RuleAcceptor runtime machinery), so reusing it would either break serialization of Language or pull in plugin-system coupling. This minimal data-only version keeps Language serializable end to end while preserving the same id-keyed identity semantics.

Module: transform_def ​

Transform rule fragment definitions (ADR-0094 — Generic AST Transform Engine). Transform rule fragment definitions (ADR-0094 — Generic AST Transform Engine).

A transform is a pure Ast → Ast rewrite: it never evaluates, typechecks, or emits. A pass is a named, ordered set of transform rules (e.g. desugar, lower, optimize). A [TransformDef] maps a node kind to a rewrite within a pass; the Language transforms fragment set is the dispatch table a transform engine reads.

This crate holds only the data: [TransformRule], [RewriteStep], and [TransformCondition] are the rewrite vocabulary — they are interpreted by transform engines (e.g. hnl-engine-transform-rewrite), never executed here. The Native rule variant and the Splice/Apply/PayloadEq vocabulary are declared now so the schema is complete; they need no runtime support in this crate.

Serde representation ​

All enums use serde's default externally tagged representation — matching every other enum in this crate (AstDesugarChild, LexerPattern, …). A rule is {"Declarative": {"target_kind": …, "children": […]}} or {"Native": "desugar.while"}; a step is {"Keep": 0} / {"KeepRole": "target"} / {"Create": {…}}; a condition is {"KindAt": {…}} / {"And": […]} / etc. JSON and YAML round-trip identically.
