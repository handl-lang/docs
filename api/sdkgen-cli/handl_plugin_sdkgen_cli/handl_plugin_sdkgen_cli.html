Module: backend ​

The cli [SdkgenBackend]: *.clispec.yaml files load directly; recognized foreign specs (fig, cli-schema — see [crate::foreign]) ingest into the same IR; anything else is a tool name (or path) probed via --help.

A spec file carrying a probe: block also probes name and overlays the authored commands on the discovered tree — authored nodes win field-by-field, so a spec can declare only the tree shape and let probe fill in options.

Module: config ​

*.sdkgen.yaml configuration overlay for the cli backend.

yaml
rename: { "pr.create": "make" }       # rename a command (dotted path)
drop: ["pr.delete"]                   # remove a command subtree
types: { "pr.create.reviewers": strings }  # override an option/positional kind
max_depth: 2                          # probe recursion cap
emit_spec: gh.clispec.yaml            # dump the resolved tree ("-" for stdout)

The overlay is applied after spec load or probing. All dotted paths refer to the original command names — drop/types run before rename, so a renamed command's new name is not a valid types key.

Module: emit_hnl ​

hnl-cli emitter: <module>.hnl port + adapter pair for CLI specs.

The port declares each leaf command as export {Port}: ({args}) ~[1]~> Result<Output, Spawn>; the adapter (in the sibling {lib}-cli-{slug} package) binds it to cli-c's runner:

text
export gh_pr_create: GhPrCreate := (branch, opts, extras) ~> do {
  run(argv("gh", ["pr", "create"], [branch], gh_pr_create_flags, opts, extras))
}

cli-c contract (the host-side package the adapter imports):

  • run: ([String]) ~[1]~> Result<Output, Spawn>
  • argv: (String, [String], [String], [FlagSpec], Obj, [String]) ~> [String] — (prog, subpath, positionals, flag specs, opts record-or-null, rest). cli-c stringifies scalars and expands opts fields per each spec's kind.

Argument docs (the descriptor's optional trailing :<doc> component — the tool's help-table one-liner) thread through to the generated SDK docs: the adapter's FlagSpec entries carry a doc: "<one-liner>" string (empty when unknown), and the port's fn doc comment grows --- opts:/--- args: tables for the args that have one.

Module: foreign ​

Foreign CLI spec ingestion — spec formats from other ecosystems lowered into the [CliSpec] IR.

Three dialects are recognized, one file each (plus the shared detection/lowering helpers here):

  • fig ([fig]) — a serialized withfig/autocomplete completion spec: the subcommands / options / args tree. *.fig.json and *.figspec names claim it outright; any other JSON file carrying a subcommands array or fig-shaped options rows ({"name": ["--long", "-s"], …}) is sniffed as fig.
  • cli-schema v1 ([cli_schema]) — the cli-schema agent-facing document: schemaVersion, commands / namespaces, parameters with role / type. *.cli-schema.json names and the schemaVersion / cli-schema-version markers select it.
  • usage ([usage], on the [kdl] reader) — the usage spec: KDL flag "-f --force" / arg "<x>" / cmd "name" { … } trees (mise ships one). *.kdl / *.usage.kdl names claim it; content is sniffed when a document parses as KDL and carries top-level cmd/flag/arg/option/usage nodes.

Constructs with no IR analog but useful meaning — fig suggestion generators, cli-schema intent/environment declarations — degrade into bracketed doc annotations ([generator: filepaths], [intent: destructive, scope: global], [env: GITHUB_TOKEN (required)]), the same convention exclusiveOn/dependsOn/ aliases/required already use. Anything else unrecognized is dropped with a warning naming it (fig git.checkout: unsupported subcommand fields dropped: loadSpec).

Module: help ​

Pure parser for --help text — usage lines, option/positional/ subcommand tables — plus parse-confidence diagnostics. No process spawning lives here; [crate::probe] feeds captured output to [parse_help].

Recognized shapes (cobra/clap/getopt/argparse conventions):

  • Usage: gh pr create [<flags>] <branch> [<revs>...] — <x>/[x] positionals, x.../[x]... variadic → rest, {a,b}/{a|b} choice groups → subcommands, [OPTIONS]/[COMMAND] markers skipped. Usage: alone takes the next indented line (cobra/go), and indented continuation lines are alternate forms (or:-led alternates are ignored). SYNOPSIS-headed man pages feed the same path. Parenthesized alternation groups ((TYPE NAME | -f FILE)) are modeled, not skipped: an all-positional alternation emits alternative[0]'s positionals ((TYPE NAME | TYPE/NAME) → type, name), a flag-bearing one flattens to a named rest tail with a warning, and quoted option values (--schedule='0/5 * * * ?') stay single tokens.
  • Flags:/Options:/Global Flags:/Valid options are: tables — rows like -t, --title <string>, --draft, --opt=VAL, and single-dash longs (-cipher, -version). kubectl's --flag=<default>: rows and man pages' --flag (boolean) both parse; boolean-ish metavars (=false, (boolean)) mean flag kind, not string. Repeatable value-taking options — ... or []/[=VAL] markers in the spec, a plural VALS metavar, or "multiple times"/"(repeatable)"/"comma-separated" phrasing in the row — infer strings (repeat-emits flag <v> per element); a repeatable no-arg switch (-v...) stays flag. Blank lines do not close a table while the following row stays indented — kubectl and groff separate every row with a blank plus a description paragraph.
  • Commands:/Available Commands:/The commands are:/ SUBCOMMANDS: tables — rows like pr Manage pull requests. Stretches under unrecognized headers (git's start a working area (see also: …) prose) whose rows are command-shaped — name desc or * name bullets (aws's Available Services) — are promoted to subcommands when they dominate the block.
  • positional arguments:/Arguments:/Args: tables — row descriptions annotate the usage-line positionals (and {a|b} rows describe usage-group subcommands).

Anything recognized as table-shaped but unparsed lands in [ParsedHelp::warnings] — the aCLImatise/cli-to-js lesson is that --help scraping must report how confident it is, not silently emit a half-empty SDK.

Module: map ​

Lowering a [CliSpec] command tree into [SdkgenModule] IR.

One [Function] per leaf command — a node with commands is a branch (gh pr) and produces no function of its own. A tool with no subcommands is a root leaf and emits a single {tool} function.

The arg_descriptors contract ​

Emitters reconstruct argv shape from descriptors alone:

  • pos:<name> — a positional, in argv order.
  • opt:<kind>:<name>:<flag> — a named option (kind ∈ flag|string|int|strings, flag the literal spelling).
  • rest:<name> — the variadic tail.
  • meta:<hint> — emitter hints, not argv shape (e.g. meta:json-capable when the command offers a --json/--format/ --output/-o flag). Emitters ignore meta: when rebuilding argv.

Every pos:/opt:/rest: descriptor may carry a trailing :<doc> component — the argument's one-line description from the tool's help table (or an authored/foreign spec), threaded through to the emitted SDK docs. Names, kinds, and flags are validated colon-free, so the doc is simply everything past the third separator and may itself contain colons; empty docs append nothing, keeping doc-less descriptors byte-identical.

port_args aligns: one arg per positional (String/Int/Bool), a trailing opts: Obj iff the command has options, and rest: [T] last when variadic. return_port is Output / descriptor cli.

Module: probe ​

Live probing of a CLI tool's --help output into a [CommandNode] tree.

[probe_tool] runs <tool> [path...] <flag> for each candidate help flag in turn — the configured flag, then --help, -h, help, and a bare invocation — and keeps the first output that parses (git wants -h, the openssl family wants help). The result is parsed with [crate::help], its warnings land in [ProbeResult::diagnostics], and the worst per-node confidence becomes [ProbeResult::confidence]. Discovered subcommands recurse up to max_depth. The runner is injectable (&dyn Fn) so tests never spawn a process; [CommandRunner] is the real std::process implementation used by the backend.

Module: spec ​

The authored *.clispec.yaml spec format for the cli backend.

A spec names a tool (name) and its command tree (commands), each node carrying about docs, options, positionals, an optional variadic rest tail, and nested commands. The top-level spec is itself a command node (flattened), so a tool with no subcommands declares its options/positionals at the root.

yaml
name: gh
about: GitHub CLI
commands:
  pr:
    about: Manage pull requests
    commands:
      create:
        about: Create a pull request
        options:
          title: { flag: "--title", kind: string, doc: "PR title" }
          draft: { flag: "--draft", kind: flag }
        positionals: [{ name: branch, kind: string }]
        rest: { name: extras, kind: string }
