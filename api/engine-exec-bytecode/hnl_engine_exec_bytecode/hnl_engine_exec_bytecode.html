Module: compile ​

Term -> v2 bytecode compilation (ADR-0052 Phase B).

The [compile] function translates a [Term] combinator tree into a flat Vec<Instr> program. Each combinator maps to a fixed instruction sequence -- see the [crate::instr] module for the full mapping table.

Every compiled program ends with [Instr::Return]. Sub-schemes are inlined (their instructions are appended without a trailing Return) so that exactly one value remains on the operand stack when the program completes.

Scope discipline ​

Only extend_env pushes a scope. compile_into returns true when the compiled code pushes a scope that the caller is responsible for popping. Seq pops the scope its fst reported after snd completes (emitting [Instr::PopScope]), and propagates whatever snd reported. First/Choice/Loop/App pop any scope their sub-evaluation pushed immediately after it completes. A bare extend_env at the top level is balanced by [compile] appending a [Instr::PopScope] before Return. This mirrors the tree-walk's did_push discipline exactly.

Module: instr ​

V2 bytecode instruction set for the arrow-calculus kernel (ADR-0052).

Each Instr::Term combinator compiles to a flat sequence of [Instr] values. The v2 VM executes them against an operand stack and a scope stack, producing values identical to the v2 tree-walk reference handler.

The ISA covers the six arrow-calculus primitives.

Derived step ops ​

All four derived step ops from ADR-0052 are supported by the v2 bytecode VM:

  • loop_step (the ergonomic loop surface lowering): its carried sub-scheme arg (the body closure) is compiled inline like any other Arr.arg; the NativeOp handler recognizes loop_step via op_is_derived_step and additionally pops the loop pair (in, state) left on the operand stack by the enclosing Loop, passing it as incoming to VmFrame::apply_native_v2. The body closure is then applied via VmFrame::apply_app (recursive exec_node).

  • while_step/for_step/fix_step (built by plugin-lib-stdlib::arrow_iter::{while_loop,for_loop,fix_loop}): these carry cond/body sub-schemes that must be re-evaluated per iteration with the current value (extracted from the loop pair) as incoming. The compiler emits a [Instr::DerivedStepOp] instruction that stores each arg as an instruction range (start, end). A Jump before the sub-programs skips them during normal execution; the DerivedStepOp handler re-executes them via VmFrame::exec_instrs with the current value as incoming, then dispatches to VmFrame::apply_native_v2 with the fresh results and the loop pair as incoming. The produced Either is pushed for [Instr::LoopCheck].

Module: vm ​

Bytecode VM internals: scope stack, numeric helpers, and the execution frame.

[VmFrame] executes a compiled Vec<Instr> program against an operand stack and a scope stack. [Instr::EvalChild] and [Instr::Call] recurse into [VmFrame::exec_node], which compiles the node's scheme (via a per-node cache) and executes.

Value shapes ​

The v2 VM operates on the same tagged JSON value shapes as the v2 tree-walk handler:

  • Pair (first): {"__pair__": [a, b]}.
  • Either (Choice / tag): {"__either__": "left"|"right", "value": v}.
  • Arrow-value (App): {"__arrow__": true, "params": [...], "body_def": {"__ast__": &lt;arena>}, "binds": {...}, "handlers": [...]} — self-contained serializable data (ADR-0106).

Loop execution model ​

[Instr::LoopCheck] implements causal/strict feedback. The compiler emits Push(Null), Pair to seed the initial pair (incoming, Null), then the body code, then LoopCheck(loop_back). Each iteration: the body consumes the pair from the stack and leaves its result. LoopCheck pops the result and inspects its shape:

  • Either left -> push the carried value, fall through (done).
  • Either right -> the carried value is the new state; reconstruct pair(original_input, new_state), push it, jump to loop_back.
  • Pair (not an Either) -> single-step mode: push fst, fall through.

A max-iteration counter (100_000) prevents infinite loops. The original_input is saved by a look-ahead in the Push handler: when Push(Null) is followed by Pair and no loop is active, the stack top (the incoming value) is saved as loop_input before Pair consumes it.

Native ops and incoming ​

In the tree-walk, incoming is passed explicitly to each eval_inner call. In the VM, the incoming value flows through the operand stack. For 0-arg native ops that use incoming (id, tag, is_pos, dec, inc, half_floor, inc_fst, countdown_step, infinite_step), the incoming value IS the top of the stack -- the op pops it and pushes its result. For ops with args (add, sub, etc.), the args are on the stack and incoming is not used. For closure (0-arg, no incoming), nothing is popped.

Derived step ops ​

All four derived step ops from ADR-0052 are supported:

  • loop_step (the ergonomic loop surface lowering): the NativeOp handler pops the loop pair from the operand stack (below the inline-compiled args) and passes it as incoming to VmFrame::apply_native_v2, which applies the body closure via VmFrame::apply_app.
  • while_step/for_step/fix_step: the DerivedStepOp instruction re-evaluates the arg sub-programs per iteration with the current value (extracted from the loop pair) as incoming, then dispatches to VmFrame::apply_native_v2. See the [instr] module docs for details.
