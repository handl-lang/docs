A foreign-function entry for the [Instr::Ffi] hardware boundary.

Each entry is a closure that receives the popped argument values (as serde_json::Value) and returns a result value or an error message. The registry is keyed by (module, name); when Ffi does not find an entry it falls back to the existing [Instr::ForeignOp] dispatch via [ModuleLookup].

hnl_engine_exec_bytecode::vm::STACK_RED_ZONE ​

Constant: usize

Remaining-stack budget at which [stacker::maybe_grow] moves the next eval step onto a fresh segment. The instruction loop is iterative, but nested node evals and arrow applications still recurse natively (exec_node_inner → exec_instrs_inner → apply_app → apply_arrow_body → exec_node_inner), so a self-recursive arrow overflows the platform stack at a few thousand calls — same seam as the tree-walk engine's STACK_RED_ZONE.

hnl_engine_exec_bytecode::vm::ScopeStack ​

Struct

A scope stack: a flat Vec<(Rc<str>, TaggedValue)> of bindings with scope markers, searched innermost-first.

Mirrors the tree-walk's ScopeStack exactly: push_scope records a mark; lookup searches innermost-first (linear scan from the end); arrow applications install the arrow's residual binds as captured_root, bind params, evaluate the body_def arena, then restore. For the small scopes typical in handler programs (3-10 variables), a linear scan is faster than HashMap because there is no hashing overhead.

Clone: multi-shot resume snapshots the handle-entry environment into a replay journal so each resume re-run starts from the same scope state (mirrors the tree-walk entry_env clone).

hnl_engine_exec_bytecode::vm::op_is_derived_step ​

Function

Whether a native op is a handler-interpreted derived step op (ADR-0052 §"Derived forms"). These ops carry sub-scheme Arr.args compiled inline and consume the loop pair (in, state) that the enclosing Loop combinator left on the operand stack below those args. The NativeOp handler pops the args first, then pops the pair as incoming, before dispatching to VmFrame::apply_native_v2.

loop_step (the ergonomic loop surface lowering) and fold_step (the ADR-0120 loop fold node) are handled here — their step arg is a closure evaluated once, then applied per iteration via VmFrame::apply_app. The remaining derived step ops (while_step/for_step/fix_step) use the [Instr::DerivedStepOp] instruction instead, which re-evaluates their cond/body sub-programs per iteration with the current value as incoming.

rust
fn op_is_derived_step(op: &str) -> bool
