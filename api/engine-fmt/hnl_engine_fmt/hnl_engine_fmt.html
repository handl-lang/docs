hnl_engine_fmt::FormatEngine ​

Struct

A data-driven AST formatter that reads Language data to produce surface syntax.

The engine builds a reverse index from lang.grammar (node kind → grammar row) on each format call, then recursively walks the Ast arena. Kind→syntax mapping is entirely data-driven; the only fixed logic is the rendering strategy (infix / prefix / delimited / leaf), which is part of the calculus vocabulary.

hnl_engine_fmt::PreserveEmitter ​

Struct

A preserving AST→source emitter.

Walks a transformed AST and splices source text for every unchanged subtree (using the spans recorded by the Pratt parser), falling back to the data-driven formatter for any node produced by a rewrite or created by one. Children of changed nodes are still emitted preserving where their own spans indicate they came from the original source.

Module: layout ​

Layout rules for the token-stream formatter (ADR-0095, stage 2).

The layout stage decides how adjacent inline tokens join (spacing) and how indentation follows bracketing. Decisions are driven by Language data — [classify_token] reads TokenKindDef::category/label (ADR-0044) — so the spacing vocabulary is language-generic, matching the AST emitter's grammar-driven rendering.

Each concrete canonical style is a [FormattingRule]; the v0.1 canonical spacer (needs_space traffic, ADR-0086) is [CanonicalFormattingRule]. A different dialect or style swaps in new rule objects without touching the render stage ([crate::token::TokenFormatter]).

Module: post_process ​

Post-processing stage (ADR-0095, stage 4).

The post-process stage turns laid-out text into canonical file text: trailing whitespace removal, blank-line collapsing, blank lines between top-level declaration groups, and a single trailing newline. Each concern is a separate [PostProcessRule]; [canonical_post_process] composes the canonical v0.1 set (ADR-0086) in the required order.

Like the layout stage, post-processing is a seam: a host or kit can swap, drop, or insert rules for a different dialect without touching the render stage ([crate::token::TokenFormatter]).

Module: token ​

Token-stream render stage (ADR-0095, stage 3).

[TokenFormatter] turns a lexed token stream into laid-out source text by walking tokens in order, preserving the original line structure (newlines, blank lines, and leading whitespace) while applying the active [FormattingRule]'s spacing decisions for inline tokens. It is the "render" half of the canonical source→source pipeline; the post-processing stage ([crate::post_process]) follows it.

The formatter is agnostic to which style is active: spacing comes from the injected [FormattingRule]; token start/end offsets are used to recover the original leading whitespace and blank lines.
