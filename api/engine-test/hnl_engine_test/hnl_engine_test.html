Module: config ​

Run configuration: the planner/policy seam (ADR-0089 §"Planner + Scheduler").

[RunConfig] bundles everything the run stage needs — the selection [Filter], the [SchedulePolicy] for the generic BoundedScheduler, an optional [TestRunCache] (--cache), and an event sink — so the hnl test --filter/--jobs/--cache flags map onto a single entry point, [run_with_config].

The existing [crate::runner::run], [crate::runner::run_with_filter], [crate::runner::run_selected], and [crate::runner::run_selected_cached] functions are thin wrappers over this entry point.

Module: events ​

Structured run events (ADR-0089 §"Observability: structured events from day one").

The runner emits a [TestEvent] for every stage transition a consumer might care about: run lifecycle (RunStarted/RunFinished), suite lifecycle (SuiteStarted/SuiteFinished), discovery (TestDiscovered), selection (TestSelected), execution (TestStarted/TestFinished), and outcome refinements (TestCached, TestSkipped, TestFailed).

Collection, not a bus ​

A generic multi-subscriber event bus is explicitly deferred until a second consumer appears (ADR-0089 §"Generic infrastructure dependencies" lists "event bus" as a candidate for extraction). Today events are collected into a plain Vec<TestEvent> supplied by the caller — see [crate::config::RunConfig::events] and [crate::provider::TestProvider::discover]. The vocabulary and the collect-then-consume shape are written so that extraction is a move, not a redesign.

Determinism ​

Events are emitted in canonical plan order by the run coordinator, never from scheduler worker threads, so parallel execution changes timing but never event ordering (ADR-0089 §"Determinism").

Module: framework ​

Test framework assert side-channel (ADR-0092) ​

The pure-handl test framework now lives in handl-packages/test/ and is registered by the canonical kit (kit-canonical). This crate only keeps the thread-local side-channel used by the tree-walk assert keyword handler to store structured failure detail for the runner.

Module: provider ​

Test providers (ADR-0089 §"Providers (extensible from day one)").

A [TestProvider] turns a source of tests into a [TestPlan]. The runner never cares where tests came from; providers are the seam that lets non-filesystem sources (in-memory buffers, IDE documents, naming conventions) plug in later without modifying the runner.

Built-in providers:

  • [FileSystemProvider] — discovers .hnl/.handl files under the given paths and parses them with the canonical kit ⊕ test-language fragment.
  • [ChangedProvider] — wraps [FileSystemProvider] and only surfaces tests in files that changed according to git status --porcelain.

The future UnitProvider/PropertyProvider/DoctestProvider/… split in the ADR is deferred: discovery currently recognizes all declaration kinds in one pass via data-driven name/body roles (ADR-0081), so splitting by kind is a composition question, not a discovery-mechanism question.

Module: report ​

Reporting pipeline (ADR-0089 §"Reporting pipeline").

Reports are produced in stages and stay structured until the very end:

text
Result[] → Summary → Report → Formatter
  • [summarize] reduces a [RunReport]'s outcomes into a [Summary] (counts, total duration, slowest test).
  • A [Reporter] renders (&RunReport, &Summary) into a final string. [HumanReporter] is the console formatter; [JsonReporter] is the machine formatter. Future JunitReporter/TapReporter/CiReporter implement the same trait — --report json|junit changes no execution.

The existing [crate::runner::format_report_human] and [crate::runner::format_report_json] functions are thin wrappers over these reporters.

Module: runner ​

Bootstrap test runner (ADR-0089).

Discovers, runs, and reports tests written in handl. The runner parses modules with the canonical kit's Pratt parser, extracts test declarations (bindings whose name starts with test_ or test-language test/property etc. forms), and evaluates each test body with the tree-walk eval engine. Failures surface as result.err(...) values from the keyword assert form; the runner catches those and records structured failure detail.

Test declaration convention ​

The v0.1 grammar (ADR-0074) does not yet have a test keyword. The runner uses a naming convention: any top-level binding whose name starts with test_ is treated as a test case. The test body is the binding's value expression. For example:

handl
test_addition = 1 + 1
test_failure = assert false

The first test passes (the expression evaluates without error); the second fails (the assertion returns a result.err value). If the grammar later gains a test keyword, the runner also checks for node kinds containing "test" (see discover_tests_in_module).

Determinism ​

Tests run in source order per module; modules are processed in lexicographic order by path. No shared state between tests (handl has no mutation primitive — this falls out of the language).

Engine genericity (ADR-0081) ​

Child positions are resolved via [Language::child_role_index], never by hardcoded kind == "assign" checks. The runner resolves the target and value roles for each binding node; it falls back to positional children (0 = target, 1 = value) only when no roles are declared.
