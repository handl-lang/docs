handl_plugin_lib_handl::HandlModule::instantiate ​

Function

Instantiate a sibling module under a different dependency environment (ADR-0156).

The returned [HandlModule] shares this module's prepared source, language, eval engine, op functions and value names, but its env is env — this module's own dependencies/global_lookup/ import_resolver/default_env are not carried over. A fresh module_id is allocated through the same rebuild_functions path, so the per-thread runtime/AST caches key the two instances apart: each evaluates the same source against its own dep bindings.

self is unchanged; each instance owns its own [HandlFunction]s bound to its own module_id.

rust
fn instantiate(self: &Self, env: ModuleEnv) -> Self

handl_plugin_lib_handl::HandlModule::module_id ​

Function

The current module ID — the key into the per-thread RUNTIME_CACHE/AST_CACHE/MODULE_VALUE_CACHE tables.

Exposed so hosts (and tests) can observe that [instantiate][Self::instantiate] / with_dependency* re-keyed the caches: two [HandlModule]s with different module IDs evaluate against disjoint per-thread cache entries even on the same thread.

handl_plugin_lib_handl::HandlModule::new ​

Function

Create a new HandlModule with the given name, .hnl source, and function (record field) names.

The source should evaluate to a record of arrows (functions). Comment lines (-- ...) and cap/op/handl declaration lines (ADR-0077) are stripped automatically. Each name in func_names becomes a callable function that evaluates (source).name(args) on call.

rust
fn new<impl Into<String>>(name: impl Trait, hnl_source: &str, func_names: &[&str]) -> Self

handl_plugin_lib_handl::HandlModule::with_default_env ​

Function

Install a [DefaultEnv] provider — ambient names materialized as env globals at the lowest precedence (ADR-0155 Phase 3).

Declared deps shadow it ([build_runtime] merges dep globals over the default layer), and import splices / local bindings shadow both. Names bound here resolve scope-first as records of wrapper arrows; names bound by neither layer still fall back to the unbound→string callee path and the global_lookup leaf.

The canonical provider is plugin-lib-stdlib's std_default_env, which binds every module-table name — wired by its build_module.

rust
fn with_default_env(self: Self, provider: DefaultEnv) -> Self

handl_plugin_lib_handl::HandlModule::with_dependency ​

Function

Add a dependency module to be registered in the bridge runtime.

This allows the .hnl source to call module-qualified functions (e.g. math.sqrt, typeof.type_of) during evaluation. The runtime builder is updated to include the new dependency; any previously cached per-thread runtime is rebuilt on next access.

rust
fn with_dependency<impl Module + Send + Sync + 'static>(self: Self, module: impl Trait) -> Self

handl_plugin_lib_handl::HandlModule::with_global_lookup ​

Function

Attach a global [ModuleLookup] layered under the dependency registry.

When a string callee "mod.fn" is not found among the registered dependencies, it is resolved through this lookup. This is how stdlib packages reach the whole module table without pre-listing deps (see plugin-lib-stdlib's table lookup).

ADR-0155 Phase 3: this stays the leaf dispatch — the ambient names themselves move to env globals via [with_default_env].

rust
fn with_global_lookup(self: Self, lookup: Arc<dyn ModuleLookup>) -> Self

handl_plugin_lib_handl::HandlModule::with_import_resolver ​

Function

Attach the [ImportResolver] used to evaluate import/from statements found in the (prepared) .hnl source.

The runtime calls this resolver through prim_import to obtain a module's bindings; see [DependencyImportResolver] for the binding shape (string callees that dispatch through the module registry, identical to how mod.fn resolves today).

When not set, build_runtime derives a [DependencyImportResolver] from the module's resolved dependencies -- sufficient whenever every import path names a registered dependency. This explicit hook is for resolvers that build modules from a table rather than reuse the dependency list (e.g. plugin-lib-stdlib's TableImportResolver).

rust
fn with_import_resolver(self: Self, resolver: Arc<dyn ImportResolver>) -> Self

handl_plugin_lib_handl::HandlModule::with_language ​

Function

Bind this module's bridge runtime to lang instead of the process-wide [default_language] (ADR-0128 §"The 0.8 seam").

Use this for modules authored in a non-canonical language: the default covers the common case where the host installed the canonical language once at startup.

rust
fn with_language(self: Self, lang: Arc<handl_language::Language>) -> Self

handl_plugin_lib_handl::HandlModule::with_value_names ​

Function

Declare names as value exports — record fields exposed as plain evaluated values rather than string callees.

from "<mod>" import <name> binds the field's value (e.g. bool's true/false bind Bools), while function exports bind the mod.fn string callee. The names are declared by the host because distinguishing arrow fields from value fields requires evaluating the record — explicit names keep enumeration cheap.

rust
fn with_value_names(self: Self, names: &[&str]) -> Self
