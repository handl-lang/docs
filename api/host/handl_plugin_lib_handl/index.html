handl-lib-handl (generic .hnl library loader) ​

A generic crate that lets .hnl files replace hand-rolled Rust plugin-lib-* bridge crates for pure-logic libraries.

Each former pure-logic library crate (e.g. plugin-lib-stats, plugin-lib-hello — both now plugin-lib-stdlib package-table rows) had ~100+ lines of Rust bridge code that include_str!s a .hnl file, builds a cached per-thread Runtime, and evaluates a small applied expression per call. This crate eliminates that boilerplate with two reusable types:

  • [HandlModule] — implements Module, exposing every field of a .hnl record as a callable Function. Each call evaluates (source).field(args) via a cached per-thread Runtime.
  • [HandlLibraryPlugin] — implements Plugin, contributing a [HandlModule] into the platform's [ModuleRuntime] during contribute().

Key constraint (thread-local AST) ​

The tree-walk engine indexes into a thread-local CURRENT_AST arena, so a handl closure Value produced by one bridge runtime cannot be cached and called later from an outer runtime. Therefore the Runtime is cached per-thread (via [thread_local!]), and the applied expression (source).func(__arg_N) — whose text is argument-independent (arguments cross the boundary as values bound directly on the call frame) — is lexed/parsed once per (module, function, arity) into a per-thread AST_CACHE Rc<Ast> and re-evaluated per call through [Runtime::eval_shared_with_call_args], which binds args directly into the ScopeStack globals map without cloning the engine. Caching the evaluated record is not possible across the serde_json::Value boundary: arrows capture earlier do-block bindings, and materializing each arrow's env expands recursively (exponential on ~100-binding modules like str-handl).

Usage ​

ignore
use handl_plugin_lib_handl::{HandlModule, HandlLibraryPlugin};
use handl_plugin_lib_stdlib as stdlib;

const STATS_HNL: &str = include_str!("../../../handl-packages/stats/stats.hnl");
const STATS_FUNCS: &[&str] = &["sum", "avg", "product", "min", "max", "median", "stddev"];

let module = HandlModule::new("stats", STATS_HNL, STATS_FUNCS)
    .with_dependency(MathModule)
    .with_dependency(TypeModule);

// Or as a plugin:
let plugin = HandlLibraryPlugin::new("stats", "lib.stats", "lib-stats", STATS_HNL, STATS_FUNCS);
// or via the package table: stdlib::library("stats")

Text transforms (ADR-0094) ​

The text-level transform logic (strip_declaration_lines, parse_*, expand_tag_declarations, export→object rewriting, etc.) is canonically implemented in handl-packages/loader/loader.hnl — fully, in pure handl over the char/str floors. This crate keeps a two-level seam:

  • mod bootstrap — the irreducible Rust implementations. They prepare the str floor itself (str-handl needs from "char" import stripping before any loader exists — the bootstrap paradox) and are the correctness fallback: [HandlLoader] runs its module on the bytecode eval engine (HandlModule::with_eval_engine), which removed the interpreted str.*/char.* per-character cost that made the loader prohibitive under tree-walk (~59s → ~0.16s for strip_decls on the 22k-char str-handl source; see examples/loader_bench.rs).
  • [HandlLoader] / [install_loader] — the opt-in self-hosting seam. Once a host installs a loader built over char + str modules, every public transform here (and [HandlModule::new]'s analyze_source pipeline) delegates to loader.hnl, falling back to bootstrap on any loader error.

HandlModule::new_raw loads the loader itself raw, without applying those transforms to its own source.
