handl_plugin_lib_handl::AST_CACHE ​

Constant: $crate::thread::LocalKey<std::cell::RefCell<std::collections::HashMap<(usize, String, usize), std::rc::Rc<handl_language::Ast>>>>

Per-thread cache of parsed applied-form ASTs.

[HandlFunction::call] evaluates the applied expression (source).func(__arg_0, ..., __arg_{n-1}); that source text is a pure function of (module id, function name, arity) — call arguments bind directly on the call frame as __arg_N values, never as source text — so the lexed/parsed/desugared [handl_language::Ast] can be parsed once and reused across calls. This removes the per-call re-parse of the full module source that made the interpreted loader.hnl transforms pathologically slow (every nested str.* call re-parsed the ~740-line str-handl bridge source).

The cache is thread-local (like RUNTIME_CACHE) because Ast is not Send. It is keyed by module ID rather than source identity: a module's prepared source is fixed at construction, and parse does not depend on the module's dependency set (with_dependency only changes the eval-time module chain), so entries stay valid across rebuild_functions (which allocates a fresh module ID anyway).

Note: caching the evaluated module record instead of the AST is not possible across the serde_json::Value boundary — arrows in do { ... }-block modules capture earlier bindings, and materializing the record would expand each arrow's captured env recursively (exponential blowup on ~100-binding modules such as str-handl). Record construction inside the per-call eval is cheap (Rc env captures), so the AST cache is the right seam.

The process-wide default Language for [HandlModule] bridge runtimes (ADR-0128 §"The 0.8 seam").

This crate is the generic .hnl module loader — machinery that stays in platform — so it must not link handl-kit-data-prelude: the language a .hnl module evaluates under is supplied by the host instead. Hosts install it once at startup ([install_default_language], e.g. inside Kit::new); a [HandlModule] may also carry an explicit per-module language via [HandlModule::with_language]. handl_plugin_lib_handl::DefaultEnv ​

Type Alias: std::sync::Arc<dyn Fn>

A lazily materialized layer of default env globals (ADR-0155 Phase 3): ambient names a host wants bound scope-first in every eval of a module's runtime, at the lowest env precedence — declared deps shadow them ([build_runtime] merges dep globals over them), and import/local bindings shadow both (locals resolve before engine globals).

The provider is invoked once per runtime build — per module, per thread, inside the RuntimeBuilder closure — so materialization may itself evaluate modules (value projections into a dep-less sibling runtime) without re-entering the caller's construction path. The returned map is the same name → bindings record shape [dep_env_globals] produces for declared deps; the canonical producer is plugin-lib-stdlib's std_default_env, which binds every module-table name to a record of [wrap_dep_fn] arrows.

A host that wants the residual ambient instead — names unbound until the call_host leaf's ModuleLookup chain resolves them — simply does not install a provider; global_lookup is orthogonal and remains the leaf either way.

handl_plugin_lib_handl::DependencyImportResolver ​

Struct

The default [ImportResolver] used by a [HandlModule] runtime.

A .hnl import statement is evaluated by the runtime (prim_import), which asks the resolver for the target module's bindings record. Since ADR-0155 Phase 1 the payload is a callable record — one [wrap_dep_fn] wrapper arrow per function export (plus plain value exports) via [module_bindings_tagged]. Applying such a binding (m.f(x), or a bare named import f(x)) routes the arrow through the ordinary !App path, and the wrapper's callv body lands on the same call_host leaf a "<module>.<field>" string callee did — resolving through the importer's [ModuleLookup] registry, whose <module> entry comes from the dependency chain or, failing that, the injected global module lookup.

The string-callee encoding remains available via [module_bindings_object] for hosts that pin it — both encodings apply (ADR-0155 §2).

handl_plugin_lib_handl::HandlFunction ​

Struct

A callable [Function] backed by a .hnl source field.

Each call evaluates (source).func_name(__arg_N) via a cached per-thread Runtime. Arguments are bound directly on the call frame via [Runtime::eval_shared_with_call_args] (not injected as per-call engine globals), so no engine cloning occurs per call. The Runtime is built lazily on first use and reused for subsequent calls on the same thread; the applied form's parsed Ast is likewise cached per (module, function, arity) in AST_CACHE, so only the eval stage runs per call.

This type is created by [HandlModule]; you do not typically construct it directly.

handl_plugin_lib_handl::HandlLoader ​

Struct

A handle to the pure-handl loader (handl-packages/loader/loader.hnl).

The loader is a [HandlModule] built raw — its own source is the code that strips declarations, so it must not be transformed. It needs the char and str floors injected as dependency modules: char is a native floor (no loader needed) and str (str-handl) is prepared by the bootstrap transforms — this is the two-phase resolution of the bootstrap paradox.

ADR-0155 Phase 2 (§4): loader.hnl's str.*/char.* calls resolve scope-first — each dep name is bound to a record of wrapper arrows in the loader runtime's eval globals, and only the wrapper's callv leaf still dispatches "str.find"/"char.at" through the module registry. The registry is no longer load-bearing for the first hop — only for the leaf.

Once a HandlLoader is installed via [install_loader], all public transform functions in this crate (and [HandlModule::new]'s preparation pipeline) delegate to the handl implementations. Before installation, or if a loader call fails, the bootstrap module's Rust implementations are used.

handl_plugin_lib_handl::ModuleEnv ​

Struct

A [HandlModule]'s dependency environment as a first-class value (ADR-0156).

The env is the tuple [build_runtime] threads through: the dependency modules registered in the bridge runtime, an optional global [ModuleLookup] layered under the dependency registry, and an optional [ImportResolver] for import/from statements. Lifting it into a value lets one prepared source run under several dep bindings — see [HandlModule::instantiate].

Identity (ADR-0156 follow-up) ​

An env carries an env_id allocated from the same kind of global counter as [HandlModule::module_id]. The name-keyed singleton caches above HandlModule (kit caches, stdlib module_ref, loaders) historically collapsed one name to one env; env-aware variants key by (name, env_id), and the id is what makes that keying sound:

  • new/default mint a fresh id — two independently created envs are distinct even with identical contents;
  • clone preserves the id — clones are the same env, so env-keyed caches share one entry across them;
  • fork keeps the contents but mints a fresh id — the "same deps, deliberately separate cache" case;
  • the with_* builders re-mint, mirroring how [HandlModule::with_dependency] re-allocates its module_id so stale cache entries are abandoned when the dependency set changes.

Module: transform ​

Handl-authored transform rules (ADR-0094 — the Handl(rule_id) seam).

A TransformDef can name a .hnl function as its rewrite using the [NativeRewrite] dispatch spelling with a handl: name prefix:

yaml
- id: transform.mypass.foo
  pass: mypass
  node_kind: foo
  rule: !Native "handl:mymod.myfn"

handl:mymod.myfn resolves to function myfn on the [HandlModule] registered under module name mymod with a [HandlNativeRewrite] registry. The registry itself is a [NativeRewrite] — wire it into a RewriteEngine via with_native_registry, optionally layering a fallback registry (e.g. the desugar.* natives) underneath so non-handl: names keep resolving.

Value contract ​

The .hnl function is called with one argument: a JSON-shaped record serialization of the matched node —

text
{ kind: "foo",
  span: { start: 0, end: 3 } | null,
  payload: { … },               -- the node's payload minus `children`
  children: [ <node record>, … ], -- recursively serialized children
  roles: { scrutinee: 0, … },    -- shape child-roles resolved for THIS
                                 -- node (arity-aware; ADR-0081)
}

The top-level record additionally carries

text
  env: { self: <arena index of the matched node>,
         nodes: [ {index, kind, span, payload} … ] }

— a flat, index-addressed view of the whole input arena (payloads verbatim, so payload.children are arena indices into env.nodes). This is the generic declaration/environment service: a .hnl rewrite that needs to see beyond its own subtree (e.g. match resolving constructor names against the file's data declarations) navigates the arena itself instead of asking the engine for a kind-specific lookup.

It returns either:

  • null — decline the rewrite; the engine pushes the node through unchanged (children remapped), exactly like a native returning the pass-through path.

  • a node spec record { kind, payload?, children? } — a fresh node tree the engine realizes into the output arena. payload is used verbatim (excluding children, which is set from the realized children list) except that marker values inside the payload are resolved to arena indices (see below). Every element of children is itself a node spec or a marker:

    • { "__keep__": n } reuses the remapped output of the matched node's child n (n indexes the original node's children array, no matter how deeply nested the marker appears). A bare { "__keep__": n } return replaces the matched node with that child.
    • { "__keep__": [i, j, …] } is the path form — walks child i of the matched node, then child j of that node, and so on, and reuses the remapped output of the descendant at that path (the KeepPath analogue — e.g. a match arm's body two levels down).
    • { "__fresh__": "hint" } mints a unique var leaf (__fresh_<hint>_<n>; the same hint reuses the same leaf within one rule application).

    Inside a spec's payload, any value position may hold a single-key marker object { "__node__": <spec> }, { "__keep__": n | [..] }, or { "__fresh__": "hint" } — realized to the arena index of the produced node (this is how payload-carried child references like a function node's body field are expressed). Plain payload data is untouched.

Realized nodes inherit the matched node's span — the engine's documented span policy for rewrites.

Notes / rough edges ​

  • The .hnl function cannot observe or produce raw arena indices — __keep__ is the only handle onto existing subtrees.
  • Invocation goes through [HandlFunction]'s per-thread cached bridge Runtime (the pred.hnl/hnl-engine-test pattern): the node record crosses as an __arg_0 global and the result returns through the serde_json boundary, so the function must not return arrow values or other reserved-key (__arrow__/__tag__/…) shapes.
  • The bridge runtime runs its own desugar pass when evaluating (source).fn(arg); since it builds its own canonical Language, user-authored handl: rules never fire inside the bridge — no recursion through the transform engine.
  • Record-literal trap: a bare { directly after ~> parses as a block body, not an object literal — x ~> { a: x, b: y } evaluates each entry as a bare type-annot statement and returns the last entry's value (y), silently not the record. Write ~> ({ ... }). realize hints at this when a returned spec is malformed; the lint.record-as-block rule flags it statically.

handl_plugin_lib_handl::wrap_dep_fn ​

Function

Mint a wrapper arrow for a dep function (ADR-0155 §1): the callable-record payload a scope-bound env binds for name.

The arrow is params: [], rest: "args" over a callv body (data/eval.yaml eval.callv): applying it collects every call argument into args as an Arr[…] and hands that array to call_host with name as the incoming callee string — the same (name, packed-args-array) leaf an ordinary mod.fn(x) call lands on. Unlike a call-node body, callv forwards the evaluated array itself rather than re-packing it through proj_rest, so the leaf receives args[0] = the whole argument list regardless of arity (Function::call has no arity metadata — platform/src/eval.rsFunction::call).

The body_def arena is built directly (Ast::push + [handl_language::ast_value], the def_with_body precedent) — not via Ast::instantiate: the qualified name must stay an ambient lit string so it re-resolves through the applying runtime's module chain at call_host (ADR-0155 §"Wrappers are ambient re-resolution, not pinning"). Nothing is captured — binds/handlers are empty — and construction forces no evaluation.

name is the qualified leaf name the chain resolves ("mod.fn"). Mint-time resolution is deliberately not checked — there is no chain in scope here; a wrapper carried into a runtime whose chain lacks mod fails at call time (call_host: function '…' not found), the same failure an unbound dotted callee produces today.

fn wrap_dep_fn(name: &str) -> handl_value::TaggedValue
