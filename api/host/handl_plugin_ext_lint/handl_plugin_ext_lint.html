handl_plugin_ext_lint::LintContext ​

Struct

The injected lint bundle: the [Language] (carrying lang.lints) plus an optional [NativeLintResolver] that dispatches .hnl-authored handl:<mod>.<fn> rule names (ADR-0097).

Plugin: Send + Sync forbids holding a Kit (!Sync), so per ADR-0128 §"The 0.8 seam" the host assembles the kit-side pieces — kit.language() and kit.handl_lint_adapter().resolver() — and hands them in. Both halves are Send + Sync, so the context can ride inside a plugin.

Module: handl_lint ​

Handl-authored lint rules (ADR-0097 — the handl:<mod>.<fn> spelling, mirroring ADR-0094's HandlNativeRewrite for transforms).

A LintRuleDef can name a .hnl function as its check using the LintCheck::Native dispatch spelling with a handl: name prefix:

yaml
- id: lint.my-rule
  name: my-rule
  severity: warning
  message: "my-rule fired on '{name}'"
  check: !Native "handl:mymod.myfn"

handl:mymod.myfn resolves to function myfn on the [HandlModule] registered under module name mymod with a [HandlNativeLint] adapter. The adapter is a [NativeLintResolver], not a name in the map — handl: names are dynamic — so a host wires it once onto a NativeLintRegistry and every handl: rule dispatches:

ignore
let mut reg = canonical_lint_natives();
reg.add_resolver(
    HandlNativeLint::new()
        .with_module(HandlModule::new("mymod", MY_HNL, &["myfn"]))
        .resolver(),
);
let engine = LintEngine::new().with_native_registry(reg);

Contract: module-level, once per lint run ​

A !Native check is invoked once per module — [LintCtx] hands Rust natives every parsed statement plus the source text, and this adapter passes the same view through. A per-node contract was considered and rejected: LintCheck::Native carries no node_kind filter, so a per-node handl: check could express nothing that !Match { node_kind, when } (which already runs the full TransformCondition vocabulary per node) cannot. The point of a .hnl native is exactly the module-level view — scope analysis, cross-statement conventions — that !Match cannot reach.

The .hnl function is called with one argument, a JSON-shaped module record:

text
{ source: "<the module source text>",
  statements: [
    { text: "<statement chunk>",
      offset: <byte offset of `text` in `source`>,
      root: <node record> },
    …
  ] }

<node record> is the same shape transforms use — {kind, span, payload, children} with children recursively serialized — except that every span is already absolute: each statement's offset has been added, so spans read off node records can be reported verbatim in hits.

The function returns either:

  • null or [] — no violations.
  • a list of hit records:
text
{ name: "x",                        -- optional; fills the {name}
                                    --   placeholder of the rule's
                                    --   message template
  args: { "<key>": "<value>", … },  -- optional; extra {key} args
  span: { start: <byte>, end: <byte> },  -- optional; absolute
  fix: { start: <byte>, end: <byte>,
         replacement: "<text>" }    -- optional; a LintFixOut
}

(name is sugar for args.name; an explicit args.name wins.)

Notes / rough edges ​

  • Invocation goes through HandlFunction's per-thread cached bridge Runtime, exactly like HandlNativeRewrite — the module record crosses as an __arg_0 global and hits return through the serde_json boundary, so the function must not return arrow values or other reserved-key (__arrow__/__tag__/…) shapes.
  • Like HandlNativeRewrite, nothing wires this adapter in the shipped hosts yet — it is the opt-in seam a host (or lints.yaml third-party language) uses when it wants .hnl-authored lint rules.

Module: plugin ​

The lint capability plugin — the capability-contract adapter over the free functions in this crate.

The plugin holds the injected [LintContext] — the host's language plus its .hnl-rule resolver (ADR-0128 §"The 0.8 seam"); Plugin: Send + Sync forbids holding a Kit, so the kit-side pieces arrive already extracted. host-cli registers it with the thread-cached canonical kit's parts and dispatches {command: "lint", args: [...]} through the plugin-ext-* capability seam. The free functions remain the implementation.

Payload contract (capability lint) ​

json
{ "source": "<text>", "fix": false, "prelude": ["str", "map"],
  "language": { …serialized Language… } }

  • source (required, string) — the text to lint.

  • fix (optional, bool, default false) — when true, return the fixed source instead of the diagnostics.

  • prelude (optional, array of strings) — canonical wire names the checker should treat as bound. Omitted = an empty prelude.

  • language (optional, object, ADR-0124) — a serialized Language (handl-language's Language derives Serialize/Deserialize; the canonical one is ~180 KiB compact JSON). Omitted = the injected context's language.

    This exists because the caller's language and the injected default are not guaranteed identical — host-cli lints through load_canonical_language() while the injected context carries kit.language(). Passing the language makes the capability path match the direct call instead of approximating it; the injected resolver is kept either way (.hnl rules always dispatch on the host's modules).

Response ​

Discriminated by status, matching the fmt capability, so no case is inferred from a missing field:

  • { "status": "diagnostics", "diagnostics": [ <Diagnostic>, ... ] }
  • { "status": "fixed", "output": "<fixed text>" }
  • { "status": "error", "message": "<why>" } — could not lint or fix.

Only a malformed request is a [PlatformError] (bad payload, wrong capability, un-deserializable language); a parse failure is a successful response carrying an error status.
