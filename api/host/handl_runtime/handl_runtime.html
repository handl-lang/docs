handl_runtime::COMPILED_VALUE_KEY ​

Constant: &str

The sentinel object key marking a [Value] as a compiled-program handle.

A compiled-program handle is a JSON object {"__compiled__": <id>, "target": <target>}. The id references an entry in the thread-local [COMPILED_REGISTRY] carrying the non-serializable compiled artifact. The handle itself is a serializable value; the artifact is not — native code cannot be serialized into serde_json::Value.

handl_runtime::CachedModule ​

Struct

A cached evaluated module: the exported bindings record in tagged form plus the module's post-desugar AST (retained so the Value-returning [ModuleLoader::load_module] can still run [EvalEngine::seal_module_value] at extraction time).

The bindings are stored as a shared [TaggedValue] rather than a serde_json::Value: the tagged record keeps Rc-shared substructure (arrow binds maps shared across a rec region, per ADR-0106) intact, so the cache retains one copy of the module's value graph. The old Value cache pinned a fully expanded JSON tree per module — shared binds were duplicated at every arrow — which dominated resident memory on multi-file test runs (hnl test <dir>).

Fields:

  • bindings: std::rc::Rc<handl_value::TaggedValue> - The module's export record (TaggedValue::Obj in practice).
  • ast: std::rc::Rc<handl_language::Ast> - The module's post-desugar AST, kept for seal_module_value.

handl_runtime::CompiledArtifact ​

Trait

A compiled artifact — engine-specific, non-serializable, held in the [COMPILED_REGISTRY] behind a trait object.

Each compile engine (hnl-engine-exec-bytecode, hnl-engine-exec-cranelift) produces its own impl carrying the compiled artifact plus the Language and Ast it was compiled from (needed to execute: the bytecode VM lazily compiles child nodes using lang + ast; the cranelift helpers read ast node payloads and lang at execution time). run executes the artifact using the supplied module registry (for Foreign dispatch, re-attached by the runtime so the compiled program can recurse via the meta host functions).

Methods:

  • run: Execute this compiled artifact, returning the result value.
  • box_clone: Produce an owned boxed clone of this artifact.

handl_runtime::ModuleLoader ​

Struct

A self-contained module loader for import "path" statements (Phase 9.5).

A ModuleLoader owns independent clones of the lex/parse/eval engines (so evaluating an imported module never re-enters the importer's eval engine), a shared module cache keyed by canonical path, a "currently loading" set for cycle detection, and a module_root for resolving relative paths. It implements [ImportResolver]; the runtime delegates to it.

Construction (two-phase) ​

The loader's eval engine needs the loader itself as its import resolver (so nested import statements inside a module resolve through the same cache/cycle-detector). Because the engine holds an Rc clone of the loader, the engine cannot be set at construction time (the Rc would prevent Rc::get_mut). Instead, construct via [ModuleLoader::new] (engine unset), build the eval engine with TreeWalkEngine::with_import_resolver(Rc::clone(&loader)), then call [ModuleLoader::set_eval_engine] (which requires a unique Rc — call before sharing the loader).

handl_runtime::RuntimeConfig ​

Struct

Name-based engine selection for a [Runtime], resolved against an [EngineRegistry] (ADR-0047 §2).

Each field is an engine name. An empty string leaves that stage's engine unbound (the stage returns [LangError::NotImplemented] at runtime). A non-empty name requests a specific engine, resolved by [Runtime::from_registry] against the registry at build time.

This is serializable so a kit manifest or runtime configuration file can carry it as data — swapping an engine is a config change, not a recompile. Per ADR §2, the fields are required Strings (not Option<String>); RuntimeConfig::default() has empty strings (callers check for emptiness → unbound stage).

  • eval: String - The eval engine name (e.g. "tree-walk", "bytecode", "cranelift").

handl_runtime::RuntimeFactoryImpl ​

Struct

A [RuntimeFactory] that re-attaches a meta chain to sub-runtimes.

Holds an [EngineRegistry] + [RuntimeConfig] + a settable meta chain (the Rc<dyn ModuleLookup> that provides lex/parse/eval/compile/ run_compiled). The meta chain is set after construction via [RuntimeFactoryImpl::set_meta_chain], breaking the chicken-and-egg between the Runtime (which needs modules at construction) and the meta modules (which need Rc<dyn RuntimeFactory> at construction).

build creates a sub-Runtime with the meta chain re-attached (so the sub-runtime can recurse via Foreign dispatch) and self injected as a global bound to the [Language] value (ADR-0041 Phase 3).

The delegate parameter to [RuntimeFactory::build] is intentionally ignored — the meta chain (set via set_meta_chain) already includes the user delegate layered in. This is because the meta modules pass their delegate (the user delegate or chain tail) to factory.build, but build uses the pre-set meta chain (which already has the user delegate). This is correct because the user delegate doesn't change across recursion levels.

Fields:

  • registry: std::rc::Rc<EngineRegistry>
  • config: RuntimeConfig

Module: artifact_lint ​

Final-artifact lint (ADR-0154 §6) — the verification half of erasure.

After the exec-transform pipeline (desugar → typecheck → runtime_assert_pass → erase_pass → exec_erasure_pass) the runnable artifact must contain only 1-arrows and runtime values: no former applications, no metavariables, no undecided indices. This lint walks the reachable AST — from the root through payload["children"] and the audited [ARENA_REF_PAYLOAD_KEYS] — and reports every residual type-level datum:

  • Checker encodings embedded in payloads: {"__former__": …} (a former application), {"__meta__": …} (an unsolved metavariable), {"__neutral__": …} (a stuck neutral — rigid/meta/unfold head), and {"__type__": i} (a universe index Type(i)). These are the quote/lift boundary encodings the checker serializes; one present in a static payload is elaboration output that leaked into exec. Runtime-minted cells via eval/resolve never appear here — the lint applies to the compiled artifact, not to dynamic values (laws-as-values stay legal, ADR-0154 §6).
  • Undecided type-level node kinds: a kind the checker owns a typing rule for (lang.types) but no exec scheme exists (lang.eval) — e.g. pi/sigma/forall/family/j in the canonical language. Reaching exec, such a node hits the no-scheme fallback, which returns the raw payload (arena indices and all) as a "value" — the silent unsafety this lint turns into a diagnostic: a pipeline bug, or a site that needs a runtime backstop.

Nodes that are structural sub-positions rather than evaluated expressions — entry, arm, alt — carry no lang.types rule and are not flagged; literal value/lit nodes carry no child references and are likewise exempt.

The lint is a verification pass, not a typing discipline: it checks an invariant of the artifact, adding no binder annotations and no quantity system (ADR-0154 §6, ADR-0153's withdrawal of coeffect grades).

Module: desugar_pass ​

Data-driven AST desugar pass — thin delegate over the generic transform engine (ADR-0094 §6).

The "desugar" pass runs between parse and eval in Runtime::parse. Declarative AstShapeDef::desugar rules are lowered into TransformDefs in lang.transforms["desugar"] at Language::merge time (ADR-0094 §6, handl-language), and the desugar.* native rewrites (while, do-while, for, nullish, opt-chain, data, match) live in hnl-engine-transform-rewrite::native::desugar behind the NativeRewrite registry — consulted as a fallback for kinds with no declarative rule, preserving the legacy ordering.

Pipeline ordering (ADR-0082, Phase 1.2) ​

The desugar pass runs at parse time for the exec pipeline — Runtime::parse is Runtime::parse_raw + apply_desugar. This means:

  • Runtime::eval always sees the desugared AST (no raw data/while/ for/nullish/opt-chain nodes).
  • The typecheck pipeline consumes the raw AST instead: Runtime::parse_raw / Kit::parse_raw feed Kit::typecheck*, and Runtime::run_checked checks the raw AST then desugars for eval. The NBE checker's type rules and judgments are authored against source-level shapes (data → synth_data, match → synth_match_arms); desugared output mints internal nodes (lit__sym__ payloads, __former__/__ctor__ objects) that have no typing rules by design — so lex → parse → desugar → typecheck was an integration bug, not the intended pipeline.

The bootstrap check_module in hnl-engine-typecheck parses directly (without desugar) due to a cyclic dependency constraint (hnl-engine-typecheck cannot depend on handl-runtime). This is a known limitation: the bootstrap checker does not handle data declarations. The runtime pipeline (Kit/Runtime) is the recommended path for typechecking data declarations.

Module: erase_pass ​

Proof-erasure pass (ADR-0032 item 6).

After the typechecker succeeds, this pass walks the AST and replaces any node whose inferred type is a proof constructor (type.refl, type.is_evidence, or type.empty) with an erased node. The erased node has no runtime cost: it evaluates to Value::Null.

The pass is an in-place arena mutation: node kinds and payloads are rewritten, but arena indices are preserved, so all parent references remain valid.

Module: exec_erasure_pass ​

Exec-transform type-erasure pass (ADR-0154 §6, generalizing ADR-0151).

ADR-0151 established that type annotations are checker-owned static metadata the exec engine must never evaluate; ADR-0154 §6 generalizes that into a uniform rule: type-level positions erase at exec. The "exec-erasure" transform pass runs after typechecking (post runtime_assert_pass + erase_pass) and before evaluation, rewriting every node a rule declares erasable:

  • type-annot — expr : T rewrites to the subject child via TransformRule::Replace (the annot subtree becomes unreachable); shipped declaratively as transform.exec-erasure.type-annot in the canonical kit's transforms.yaml. This is the AST-level form of ADR-0151's eval.type-annot erasure — the annotation never reaches an eval scheme at all.
  • Pi/Sigma/Forall/Family type expressions and former applications (Hom/Arr/Type(i) spellings, {"__former__"} values) living inside erased positions vanish with the position. The same content in a runnable position is not erased — it is live-but-stuck code, which [crate::artifact_lint] turns into a diagnostic rather than silently null-ing it (ADR-0154 §6).
  • data declarations already desugar to former/ctor/rec bindings at parse; their type metadata surfaces as type-annot nodes inside the emitted bindings and erases with the same rule. A raw data node reaching exec is a pipeline bug — eval.data raises desugar_error.

The pass is data-driven: languages declare their own erasable node kinds as pass: "exec-erasure" TransformDefs in lang.transforms — no node-kind dispatch lives here (ADR-0044, engine-genericity). A language with no exec-erasure rules passes through unchanged.

Root-elimination and DCE ​

Replace rules map the matched node onto an existing descendant, so a root type-annot (e.g. a bare 42 : Nat program) maps the input root to a mid-arena output index and leaves the erased annotation subtree behind as unreachable arena entries. [Ast::subtree] re-lays the reachable arena post-order — dropping orphaned type-level subtrees (the dead-code half of erasure, ADR-0154 §6) and restoring the root-is-last Pratt convention the eval engines assume.

Module: fp ​

FP host functions: fn.fanout_fn, field_access ​

Host functions for the functional-programming Foreign schemes in the canonical eval data. These are the FP-relevant foreign functions that can be implemented as pure [Function] impls — they operate on already-evaluated argument values and need no access to the AST, node payload, or scope.

  • fn.fanout_fn(a, b) → [a, b] — eager fanout into a pair/tuple.
  • field_access(target, field) → target[field] — dynamic field access on an object (string key) or array (numeric index).

Constructs that require lazy evaluation or payload access (match, handle, json) are implemented as engine Prim ops, not Foreign host functions, because the [Function] trait (call(&[Value], &mut EvalContext)) provides no access to the evaluation context.

Module: module_prep ​

Text preparation for canonical .hnl modules loaded by the runtime.

This is a lightweight mirror of the export-to-object rewrite used by handl_plugin_lib_handl so that ModuleLoader can evaluate multi-export package modules without depending on the higher-level handl_plugin_lib_handl crate (which itself depends on handl_runtime).

The rewrite is structure-aware: the source is segmented into top-level statements with a bracket-depth/string/comment scanner ([top_level_segments]), so an export declaration is recognized at any statement position — after a newline, after ;, or mid-line following another statement — and its := RHS is captured whole no matter how the author laid out newlines inside do {…}/if/else blocks. A construct that cannot be transformed (an export declaration without a ::/:=/:/= separator) is a hard [LangError] — module prep never silently drops a declaration.

Module: runtime_assert_pass ​

Runtime-assert lowering pass (ADR-0068 §1 "graduated guarantees").

When the typechecker cannot normalize a predicate annotation (Verdict::Blocked), it accepts the annotation statically but records a runtime_assert diagnostic. This pass rewrites the AST so that each type-annot node whose annotation is a predicate is replaced by a runtime-assert node that evaluates the predicate at runtime and raises a LangError on failure.

The pass is an in-place arena mutation: each type-annot node has its kind changed to runtime-assert and its children reordered from [subject, annot] to [predicate, expr] = [annot, subject]. Arena indices are preserved, so all parent references remain valid.

Over-eager wrapping ​

The pass wraps all type-annot nodes, not just the blocked ones, because the typecheck diagnostics do not currently carry enough info to locate the exact annotation site. This is safe: the runtime_assert native op passes through the value unchanged when the predicate is not a closure (e.g. a plain type.number tag), so non-predicate annotations incur only one extra eval call with no behavioral change. The pass is only run when at least one runtime_assert diagnostic exists, so programs without blocked predicates pay no overhead.

Module: vm_primitives ​

VM primitives module — host functions for the exec model's VM instruction set.

exec_model.hnl (ADR-0103) defines structural ops that orchestrate VM primitives (push_scope, pop_scope, bind, lookup, call, ffi, make_closure, pattern_match, lookup_eval_scheme, setfield, ctx). These are the irreducible machine — the hardware boundary / VM instruction set. On the tree-walk runtime they are not native ops; they are host functions registered via this module so the exec model's structural ops become executable for testing.

The implementations are minimal — they handle the common cases needed by the exec model parity tests. They are not production-grade:

  • lookup_eval_scheme returns a host-function name string for simple kinds (Arr, Const); the corresponding eval_scheme_* host functions extract the value field directly. Kinds requiring recursive evaluation (e.g. Seq, Tag) are not supported — the eval scheme host function would need to call back into the exec model's eval, which is a local binding not accessible from a host function.
  • make_closure creates a closure record ({"__closure__": true, ...}); call returns the body field for closure records (cannot evaluate the body from a host function). Arrow-values are dispatched via ctx.try_call_value.
  • vm_pattern_match handles wildcard ("_"), variable (string pattern), and literal equality. Structured patterns (records, arrays, tag patterns) are not supported.
  • ffi handles a few native arithmetic ops (add, mul, sub, div); other dispatches return Null.
  • ctx / setfield manage a simple in-memory context record with handler_stack and exports fields.
