handl_plugin_ext_refinement::trait_inference::Law ​

Enum

Named equational laws between graph expressions, mirroring the Lean4 Law inductive type.

Each constructor identifies a specific law and names the combinator it applies to (first for product-functor laws, left for coproduct-functor laws). The Lean4 formalization carries type/graph parameters; the Rust port names only the law (the parameters are implicit in the Term structure being analyzed).

The four laws ​

  1. FunctorIdentity: first (idG A) ≡ idG (A × D) — functoriality of first preserves the identity.
  2. FunctorComposition: first (comp G H) ≡ comp (first G) (first H) — functoriality of first distributes over composition (fusion).
  3. CoproductIdentity: left (idG A) ≡ idG (A + D) — functoriality of left preserves the identity.
  4. CoproductComposition: left (comp G H) ≡ comp (left G) (left H) — functoriality of left distributes over composition (fusion).

Variants:

  • FunctorIdentity - first (idG A) ≡ idG (A × D) — functor identity for first.
  • FunctorComposition - first (comp G H) ≡ comp (first G) (first H) — functor composition
  • CoproductIdentity - left (idG A) ≡ idG (A + D) — coproduct functor identity for left.
  • CoproductComposition - left (comp G H) ≡ comp (left G) (left H) — coproduct functor

  • fn equation(self: &Self) -> &'static str - The equation the law states, in arrow-calculus notation.
  • fn is_functor_law(self: &Self) -> bool - Whether this law applies to the first (product functor) combinator.

This is the bridge between the trait inference (which laws a graph satisfies) and the contract inference (what refinement guarantees hold). handl_plugin_ext_refinement::trait_inference::infer_law_annotations ​

Function

Infer law-based contract annotations for a Term graph.

This is the wiring point between the trait inference and the contract inference. When a graph is recognized as satisfying a functor law, the contract inference can use this to simplify or strengthen the inferred contract.

The annotations describe the semantic consequence of each satisfied law:

  • FunctorIdentity: first(id) is the identity on A × D — the side channel is preserved exactly. This strengthens the LengthEq(input.1, output.1) guarantee that infer_r already derives for First, confirming it is an exact equality (not just length).
  • FunctorComposition: first(comp G H) = comp (first G) (first H) — the guarantee of first(comp G H) is the composition of the guarantees of first G and first H. This confirms the Seq composition rule used by infer_r is sound for First-wrapped graphs.
  • CoproductIdentity: left(id) is the identity on A + D — the right branch passes through unchanged. This confirms the Choice inference rule is sound when the right branch is an identity.
  • CoproductComposition: left(comp G H) = comp (left G) (left H) — the guarantee of left(comp G H) is the composition of the guarantees of left G and left H.
rust
fn infer_law_annotations(scheme: &handl_language::Term) -> Vec<LawAnnotation>

handl_plugin_ext_refinement::trait_inference::inferred_trait ​

Function

The set of laws inferred from a graph's wiring, by structural recursion.

This is the Rust mirror of the Lean4 inferred_trait function. It maps a graph to the list of laws it satisfies, by inspecting the wiring structure. No law is declared; the function reads the laws off from the structure.

The inference is structural:

  • A graph using first → functor pattern detected → functor laws.
  • A graph using left → coproduct functor pattern detected → coproduct functor laws.
  • A graph using neither → no laws.

Example ​

use handl_language::Term;
use handl_plugin_ext_refinement::trait_inference::{inferred_trait, Law};

// first(id) → functor laws.
let g = Term::first(Term::arr_native("id", vec![]));
let laws = inferred_trait(&g);
assert!(laws.contains(&Law::FunctorIdentity));
assert!(laws.contains(&Law::FunctorComposition));
assert!(!laws.contains(&Law::CoproductIdentity));

// id → no laws.
let g = Term::arr_native("id", vec![]);
assert!(inferred_trait(&g).is_empty());
rust
fn inferred_trait(scheme: &handl_language::Term) -> Vec<Law>

handl_plugin_ext_refinement::trait_inference::law_verified ​

Function

Whether a law is verified by CutElim normalization.

In the Lean4 formalization, LawVerified law is a Prop that holds when both sides of the law normalize to the same canonical form under CutElimStar. The theorem all_functor_laws_verified proves that all four laws are verified — with zero sorry.

In the Rust port, we take this as a proven fact: law_verified always returns true. The structural-pattern check (UsesFirst / UsesLeft) is the only runtime computation needed; the law verification is a theorem, not a runtime check.

This mirrors the Lean4 design where SatisfiesLaw G law is UsesFirst G ∧ LawVerified law — the LawVerified conjunct is theorem-level (always true), so the runtime work is entirely in the UsesFirst / UsesLeft recognizer.

rust
fn law_verified(_law: Law) -> bool

handl_plugin_ext_refinement::trait_inference::satisfies_law ​

Function

Whether a Term graph G satisfies law.

This is the Rust mirror of the Lean4 SatisfiesLaw G law predicate. A graph satisfies a law when:

  1. G's wiring exhibits the structural pattern the law applies to (UsesFirst for functor laws, UsesLeft for coproduct-functor laws), AND
  2. The law is verified by CutElim normalization (LawVerified law).

Since all four laws are proven verified in the Lean4 formalization (zero sorry), condition (2) always holds. The runtime computation is entirely in the structural-pattern check.

Inference theorem ​

The Lean4 inference theorems (satisfies_functor_identity, etc.) state: if G uses first, then G satisfies the functor identity and composition laws — without the law being declared. This function implements that inference: given a graph and a law, it checks whether the graph's wiring matches the law's pattern.

Example ​

use handl_language::Term;
use handl_plugin_ext_refinement::trait_inference::{satisfies_law, Law};

// first(id) uses first → satisfies FunctorIdentity.
let g = Term::first(Term::arr_native("id", vec![]));
assert!(satisfies_law(&g, Law::FunctorIdentity));
assert!(satisfies_law(&g, Law::FunctorComposition));
// first(id) does not use left → does not satisfy CoproductIdentity.
assert!(!satisfies_law(&g, Law::CoproductIdentity));
rust
fn satisfies_law(scheme: &handl_language::Term, law: Law) -> bool

handl_plugin_ext_refinement::trait_inference::uses_first ​

Function

Whether a Term graph uses first — i.e. Term::First appears anywhere in its wiring.

This is the Rust mirror of the Lean4 UsesFirst inductive predicate. A graph uses first if:

  • It is a Term::First { .. } node (the here case), OR
  • It is a Term::Seq { fst, snd } and either fst or snd uses first (the leftComp / rightComp cases), OR
  • It is a Term::Loop { body } and body uses first, OR
  • It is a Term::Choice { l, r } and either branch uses first, OR
  • It is a Term::App { callee, args } and the callee or any arg uses first.

Term::Arr nodes never use first (they are base arrows).

Example ​

use handl_language::Term;
use handl_plugin_ext_refinement::trait_inference::uses_first;

// first(id) — uses first directly.
let g = Term::first(Term::arr_native("id", vec![]));
assert!(uses_first(&g));

// comp(first(id), id) — uses first in the left component.
let g = Term::seq(
    Term::first(Term::arr_native("id", vec![])),
    Term::arr_native("id", vec![]),
);
assert!(uses_first(&g));

// id — does not use first.
let g = Term::arr_native("id", vec![]);
assert!(!uses_first(&g));
rust
fn uses_first(scheme: &handl_language::Term) -> bool

handl_plugin_ext_refinement::trait_inference::uses_left ​

Function

Whether a Term graph uses left — i.e. the coproduct-functor combinator appears anywhere in its wiring.

In the Lean4 formalization, left F is a dedicated graph constructor that routes Left through F and Right through the identity. In the Rust Term IR, the coproduct functor is represented as Term::Choice { l: F, r: id } — the left branch is the active sub-graph, and the right branch is the pass-through identity.

This recognizer checks for Choice nodes where the left branch is non-trivial (not just an identity) — this distinguishes a genuine left(F) (coproduct functor) from a general choice(G, H) (which may be a conditional, not a functor application). The right branch being an identity (op == "id") is the hallmark of left.

This is the Rust mirror of the Lean4 UsesLeft inductive predicate.

Example ​

use handl_language::Term;
use handl_plugin_ext_refinement::trait_inference::uses_left;

// left(id) = choice(id, id) — uses left (coproduct functor).
let g = Term::choice(
    Term::arr_native("id", vec![]),
    Term::arr_native("id", vec![]),
);
assert!(uses_left(&g));

// id — does not use left.
let g = Term::arr_native("id", vec![]);
assert!(!uses_left(&g));

fn uses_left(scheme: &handl_language::Term) -> bool
