handl_platform::config::DependencySpec ​

Struct

A project dependency declared in [dependencies] (or [patch]) of .handl.toml.

The name is the import specifier's first path segment: import "arrows/transform/map.hnl" resolves inside the arrows dependency's directory.

A dependency has exactly one source:

  • path — a vendored / sibling package directory containing .hnl sources (relative to the manifest directory, or absolute).
  • git — a repo-hosted package specifier (URL or host:owner/repo shorthand, e.g. github:handl-lang/c) with an optional rev/branch/tag pin. At resolve time the name maps to the package's slot under [package_cache_dir], and the fetch-on-miss hook (ADR-0010's registry half, [fetch_dependencies]) materializes the slot — git clone + checkout of the declared selector — when it is absent. A populated slot is left untouched (no refetch, no selector check), and a [patch] entry of the same name overrides the source with a local checkout — the Cargo [patch] dev-link story (scripts/dev-link.sh), so a committed manifest can name the repo portably while a local machine resolves the sibling dir.

handl_platform::config::materialize_git_dep ​

Function

Clone spec's git source, check out the declared selector, and publish the result into slot.

The clone runs in a private temp directory ([claim_temp_slot]) and is published with an atomic rename, so concurrent fetches of the same dep (parallel hnl processes / test binaries resolving the same .handl.toml) can never observe or destroy each other's clones: the previous cleanup-on-failure removed the shared slot itself, so the loser of a clone race deleted the winner's fresh checkout and the winner's follow-up git checkout then failed with a bare "No such file or directory" (the intermittent dep-checkout build flake). A rename that finds slot already populated means another fetch won the race — a populated slot is trusted by design (fetch-on-miss never refetches), so that is success. Only the caller's own temp dir is ever removed, on failure or on losing the publish race; a crash mid-fetch leaves a dot-prefixed temp behind, never a half-cloned slot that would be mistaken for populated.

rust
fn materialize_git_dep(slot: &std::path::Path, spec: &DependencySpec) -> Result<(), String>

handl_platform::config::resolve_dependencies ​

Function

Read <manifest_dir>/.handl.toml and resolve its [dependencies] and [patch] tables into an import-name → absolute package-directory map.

Dependency paths are relative to the manifest directory; absolute paths are honored as-is. A missing manifest yields an empty map (no dependencies). A present-but-unparseable manifest is an error — silent fallback would make import failures look like missing files rather than a broken manifest.

The git-package→dir bridge ​

A [dependencies] entry may name its package portably by git source — host-tensor = { git = "https://github.com/handl-lang/lib-host-tensor", tag = "v0.1" } — instead of a machine-local path. Such an entry resolves to its [package_cache_dir] slot, and resolution is fetch-on-miss: when the slot is absent and no live [patch] shadows the name, [fetch_dependencies] clones the declared repo and checks out the selector before the map is built (ADR-0010's registry half). The [patch] table is the consumer-supplied local override for the same names — the Cargo [patch]/dev-link story (scripts/dev-link.sh):

toml
[dependencies]
host-tensor = { git = "https://github.com/handl-lang/lib-host-tensor", tag = "v0.1" }

[patch]
host-tensor = "../lib-host-tensor"   # sibling checkout, machine-local

A patch entry wins when its named directory exists; a patch that names a missing directory is inert and the declared source applies, so a committed manifest resolves the sibling checkout where one is linked and the package cache elsewhere. [patch] may also name a package [dependencies] does not declare — it simply enters the map like a dep entry.

A failed fetch is not a resolution error: the name still maps to its (absent) cache slot with a warning on stderr, so an import of the package fails naming the directory the fetch would populate — the same failure shape as before the fetch hook existed. A populated slot is never refetched (no selector check — pins are trusted once materialized), and HANDL_PKG_FETCH=off (or 0/false/no) disables the fetch entirely for offline/hermetic runs.

This is the seam that lets .hnl packages import each other by name across repository boundaries (ADR-0128 Phase 5): from "ws-c" import … or from "libc/socket" import … resolves through the table instead of a ../ filesystem path, so a consuming repo declares the dep once in its manifest — the Cargo-dep analogue for .hnl sources.

Errors ​

Returns [PlatformError::InvalidMetadata] if the manifest exists but cannot be read or parsed.

rust
fn resolve_dependencies(manifest_dir: &std::path::Path) -> Result<std::collections::HashMap<String, std::path::PathBuf>, crate::error::PlatformError>

handl_platform::config::resolve_pkg_dependencies ​

Function

Read <manifest_dir>/pkg.hnl and resolve its deps table.

pkg.hnl is the handl-native dependency manifest a package repo ships:

text
{ deps: { math: "branch:main", "math-c": "branch:main" } }

Each spec is <kind>:<ref>. Only the local-development half is resolved here: <name> maps to the sibling checkout ../lib-<name> (the lib-<package> repo convention). Fetching branch:/rev:/tag: over git is the package manager's job (ADR-0010), not the loader's, so the spec is accepted but the ref is not acted on yet.

A missing file yields an empty map. A malformed pkg.hnl also yields an empty map rather than an error: the file is authored by package repos this workspace may not own, and a bad one would otherwise break unrelated builds. .handl.toml stays the authoritative, validated manifest.

Errors ​

Reserved for future validation; currently always Ok.
