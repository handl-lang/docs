handl_plugin_lib_stdlib::packages::TABLE_IMPORT_IN_PROGRESS ​

Static

Shared same-thread self-import guard (keyed by (thread, name)): a spec whose source basename-normalizes to its own name recurses through eval → import → resolve → bindings → eval forever, and the loop crosses instances — every build_module wires a fresh TableImportResolver, so a per-instance set never sees the re-entry. (The historical case: icu-uc-c-linux-x86_64/uchar.hnl imported ../icu-uc/uchar — basename uchar resolving back to itself. The port/adapter _c split renamed the adapter to uchar_c, so its import now lands on the uchar port row; the guard still covers any future same-basename spec.) A static is shared by every resolver; a different thread resolving the same name is a concurrent build, not a cycle (same rule as TableModuleLookup::in_progress).

rust
static TABLE_IMPORT_IN_PROGRESS: std::sync::LazyLock<std::sync::Mutex<std::collections::HashSet<(std::thread::ThreadId, String)>>>

handl_plugin_lib_stdlib::packages::TableImportResolver ​

Struct

An ImportResolver that resolves .hnl import statements through the module table.

The runtime evaluates import/from statements via prim_import, which asks the resolver for the target module's bindings record. Since ADR-0155 Phase 1 the payload is a callable record — one wrap_dep_fn wrapper arrow per function export (plus value exports as values) via [handl_plugin_lib_handl::module_bindings_tagged]. Applying a binding (m.f(x), or a bare named import f(x)) routes the arrow through !App to the same call_host leaf a "<module>.<field>" string callee dispatched to — resolving through the dependency chain or the injected global table lookup. This keeps from "x" import * as m (m.f) working and enables named imports (from "./x.hnl" import f -> bare f(...)), now with real callable values (both encodings apply — the string arm stays as fallback for hosts that emit it).

path is normalized to a module name ([normalize_module_name]) and the module is built from the table -- cached, so repeated imports of the same module never re-evaluate its source.

handl_plugin_lib_stdlib::packages::TableModuleLookup ​

Struct

A [ModuleLookup] that resolves a string callee "name.field" through the stdlib module table, building and caching the module on demand.

This is the global resolution path: a .hnl module's runtime consults it when a string callee is not found in the module's own dependency chain, so stdlib packages reach every table module without pre-listing deps. Table modules resolve through [module_ref] (a process-wide cache); names not in the table (e.g. "tag", "char") resolve through the resolver this lookup was built with, leaked once per name so lookup can return &dyn Function without holding a lock.

handl_plugin_lib_stdlib::packages::module_ref_with_env ​

Function

Get a shared [Arc<HandlModule>] for the table module name instantiated under env (ADR-0156 follow-up).

Env-aware sibling of [module_ref]: the base still comes from the name-keyed singleton (the source analysis runs once per name and is reused by every env), and the instance — [HandlModule::instantiate]d under env, which replaces the table's global lookup/import resolver with the env's — is cached by (name, env_id). Clones of one env share a single instance; distinct envs (distinct [ModuleEnv::env_id]s) get distinct module_ids.

A useful env shape is base.env().with_dependency(extra): the snapshot carries the table wiring (global lookup + import resolver) and the layered dep shadows the table for that instance (the dependency registry is consulted before the global lookup). The &'static [module_ref] singleton keeps its single-env behavior unchanged.

handl_plugin_lib_stdlib::packages::std_default_env ​

Function

A DefaultEnv provider that binds every [MODULES] table name to its bindings record — the ambient std surface made explicit (ADR-0155 Phase 3).

Scope-first layering falls out of build_runtime's merge: locals and import splices resolve first, declared deps next, these defaults last — a dep named math shadows the table's math, and a .hnl source that never declared str still finds str.trim bound.

The records are pure data minted from the spec rows ([spec_arrow_record]) — no module construction, no evaluation, no resolver. Value exports (spec.values, e.g. bool's true/false) are deliberately not projected: projecting them would evaluate the module's .hnl record during env materialization — an import cycle in any row's source would recurse (as uchar's self-import did before the *_c port/adapter split). Ambient mod.value reads were never usable anyway — an unbound bool.true evaluated to the string "bool.true", not true; via the env record it now reads Null. from "bool" import true remains the real-value binding path.

The residual ambient: non-table names the module's resolver knows (char, tag, sym, ffi, kit aliases like fn) are not bound here — they keep resolving as unbound→string callees through the global_lookup leaf, as do the field_access/fn.fanout_fn builtins. A dotted callee matching none of these layers fails at call_host (function '<name>' not found).

rust
fn std_default_env() -> handl_plugin_lib_handl::DefaultEnv
