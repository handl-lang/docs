The trait an eval engine implements.

An engine looks up lang.eval[node.kind] → [handl_language::EvalSchemeDef] → [handl_language::Term] and interprets the scheme. The engine is pure data-driven: it does not match on a static CanonicalKind enum.

hnl_engine_exec::ImportResolver ​

Trait

A resolver for import "path" statements (Phase 9.5).

When the eval engine encounters an import node, it calls the configured [ImportResolver] to load the referenced module and return its top-level bindings as a [Value::Object]. The engine then binds each entry into the current scope.

This trait is intentionally narrow: it knows nothing about the engine's internals, keeping the engine generic (ADR-0044 "language as data"). The concrete resolution strategy — file I/O, lex/parse/eval, caching, cycle detection — lives in the implementor (e.g. the runtime's module loader).

The trait is ?Send/?Sync-agnostic: it uses Rc (not Arc) to match the single-threaded eval model shared with [handl_platform::ModuleLookup].

Module: io ​

The io module — the IO<sig> effect former's surface ops (ADR-0153 §4).

perform is the op-emission primitive: perform(op, arg) mints the IO former object {"__former__": &lt;type.io sym>, "indices": [{op: arg}]} — exactly the shape [crate::native_ops::interpret_io_former] dispatches under handle <body> with <handler>: each sig entry's op name routes to the handler's matching impl with the sig entry's value as the operand, and the entry is replaced by the impl's result.

perform is a host function, not a Term::Op: the surface form is an ordinary call (perform(puts, "hi")), whose callee resolves the same way sym.seeded/type.instanceof do — the unbound var evaluates to its name string and call_host reaches this module through [handl_platform::ModuleLookup] (flat name for perform, qualified io.perform through the module-name split). Every eval engine reaches it through that single path — no per-backend arm, no grammar or eval-scheme change.

Op-name operand spellings:

  • perform(puts, "hi") — a bare identifier. Unbound vars evaluate to their name string (proj_env's unbound-to-name rule), so puts arrives as "puts". (A puts binding bound to a different value passes that value through instead — bind op names to their own name or spell them as strings.)
  • perform("puts", "hi") — the explicit string spelling.
  • perform(sym("puts"), "hi") / perform(sym.seeded("puts"), "hi") — a nominal {"__sym__": …} operand; the sym's display name is the op name.

The mint is interpret-in-place data: a perform value with no covering handler stays an IO object for an outer handler or user destructuring. Each perform mints a fresh single-entry sig — do { perform(puts, "a"); perform(puts, "b") } yields two IO values, not a merged {puts: …}; sig merging is a handle-time concern the v1 surface deliberately does not model.

Module: native_ops ​

Shared native-op semantics for the arrow-calculus kernel (ADR-0044 §7, ADR-0052).

lang.eval schemes express what a node does as Term::Op data; the op names are the calculus vocabulary and their semantics is defined once here — not re-implemented per backend. Each exec engine (tree-walk, bytecode, cranelift) is a different interpretation of the same schemes: it controls how Term is traversed and how op arguments are produced (tree-walk evaluates sub-schemes lazily, bytecode compiles them to instruction ranges, cranelift to native code), but when an op's meaning is needed it delegates to [apply_native_op] / [step_decision] with an [NativeOpCtx] implementation supplying only the engine-local globals: scope stack, node evaluation, arrow application.

This eliminates the historical 3x copy-paste of apply_native (~60 arms) plus the Num/as_num/num_value/is_truthy helpers that had already drifted apart (e.g. string add, countdown_step int preservation, Arith f64 round-tripping).

Ops that genuinely require deep engine machinery (module calls, FFI) stay behind [NativeOpCtx] services — or remain backend arms until their service is declared (imports moved behind [NativeOpCtx::import_resolver] in Phase B). [apply_native_op] returns Ok(None) for op names it does not own, so backends compose it ahead of their residual arms.

Module: pattern_match ​

Shared pattern matching logic for match/handle prims (ADR-0061).

Pattern matching interprets a pattern AST node structurally against a scrutinee value. The six pattern forms are:

  1. Wildcard — var node named _ or _* → always matches.
  2. Binder — var node with another name → binds name to scrutinee, always matches.
  3. Literal — any other node → evaluate and compare by ==.
  4. Array destructuring — array node with sub-pattern children + optional rest node → positional match, ...rest captures tail.
  5. Object destructuring — object node with entry children + optional rest node → key match, ...rest captures unmatched keys.
  6. Tag pattern — call node with a var callee (the tag name) and var arg nodes (the binders): ok(v), err(e). Dispatches on __tag__ identity and binds args to payload fields (ADR-0077).

This module is engine-agnostic. Each engine implements [PatternMatchCtx] to provide the two engine-specific operations: binding a name in the scope stack and evaluating a pattern node as a runtime value (for literal patterns). All pattern-node-kind dispatch lives here, eliminating the 3x duplication across tree-walk, bytecode, and cranelift engines.

Module: services ​

Ambient eval services shared by every exec backend.

An arrow is self-contained (body_def + binds + handlers, ADR-0106); what it needs from its host is services: the language that interprets its schemes, the module chain for host-function dispatch, host-provided globals and the import resolver. They are thread-locals because the ValueCallable seam (host functions calling arrow values) has no engine handle.

This module lives in the contract crate so no backend has to depend on another backend just to install a frame.
